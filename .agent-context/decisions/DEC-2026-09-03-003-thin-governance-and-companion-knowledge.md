## Context

Earlier work established Agent-led repository investigation, one Canonical Base and coordinated human views. A subsequent design pass expanded project-wide scanning into expert lenses, scan modes, coverage ledgers, technical-debt models and multiple governance loops. The user judged that direction too heavy in light of rapidly improving long-horizon Coding Agents and frontier models.

The user clarified that Project Cognition should not reproduce capabilities increasingly owned by LLMs. Its durable purpose is to keep Agent work aligned with project norms and task direction, judge result quality, and turn reusable knowledge produced during real work into human-friendly project material.

## Decision

1. Project Cognition is a thin, model-external governance and durable-knowledge boundary, not an expert reasoning engine or universal scanner.
2. The model/Coding Agent owns repository investigation, tool choice, work planning, reasoning, verification and presentation. The core architecture must preserve this freedom.
3. Project Cognition owns four stable concerns: task direction, relevant project policy, outcome requirements and durable-knowledge promotion.
4. User interaction remains ordinary natural language. A lightweight Task Frame may make interpreted goal, scope and completion conditions reviewable, but must not become a required user form.
5. Results are judged by whether they answer the right goal, obey relevant policy, support conclusions with proportionate evidence, expose impact and uncertainty, and return protected decisions to humans. The system does not score compliance with a fixed thought process.
6. Evidence requirements scale with claim risk. Ordinary local work remains light; global negative claims and formal gates require explicit coverage and blind spots.
7. A task result and a Knowledge Delta are separate. Only cross-task, sourced, scoped and appropriately confirmed candidates may enter the Canonical Base.
8. The Base remains the one canonical durable knowledge model, but it is intentionally thin. It does not precompute or store a complete project twin, every relation, every answer or full model reasoning.
9. Human-friendly material is generated as a downstream companion to real work using accepted Base knowledge. Articles, framework diagrams, flows, module explanations and relationship views are optional forms chosen for a reader question, not mandatory products of every task.
10. The next phase is one end-to-end Golden Run on a fixed project with no prescribed scan procedure. New Rules, Skills, Hooks, MCP services, validators, recorders or renderers are added only for observed recurring failures.
11. Core contracts remain model- and provider-neutral. Frontier models motivate the boundary but no particular Fable, Astra or other model interface becomes a dependency.

## Reasons

- Model capabilities in long-running work, repository investigation, tool use, self-verification and visual explanation will continue to improve.
- Encoding their current limitations into a permanent process would add cost and may restrict future models.
- Project goals, business meaning, accepted architecture constraints, evidence provenance and human acceptance remain external governance problems even when model intelligence improves.
- A result-oriented contract survives changes in model plans, tools and reasoning methods.
- Building human material from real work prevents a separate documentation production process and reduces drift.
- A thin Base is more likely to retain only information with real cross-task value.

## Rejected Alternatives

- Build a universal multi-language scanner: rejected because the Agent can adapt to repositories and a common parser would become a language-maintenance burden.
- Encode a mandatory expert-lens catalog and scan workflow: rejected because expert investigation can increasingly be generated by strong models and fixed procedures may constrain them.
- Make the multi-view Base Store the primary product: rejected because it starts from presentation and data modeling instead of proving the upstream work capability.
- Rely on the model with no external governance: rejected because user intent, project policy, authority, knowledge lifecycle and human acceptance still need stable ownership.
- Bind the architecture to one frontier model: rejected because model availability and capabilities change, while project governance semantics should remain stable.
- Generate documentation independently from task results: rejected because it recreates multiple truth systems and requires separate maintenance.

## Evidence

- The user stated that the proposed expert-scan system was too heavyweight.
- The user explicitly asked to account for frontier models and delegate work that LLMs can perform.
- The user stated that the system should solve norms, direction and result problems.
- The user set two current priorities: realize the target capability and use it to companion-generate a human-friendly knowledge base.
- The user explicitly authorized a backup followed by a direct reset of the entire project mainline.
- Earlier accepted decisions already established Agent-led investigation and one Canonical Base, so the new direction can retain those invariants while reducing process and data-model weight.

## Consequences

- Task Frame, Result Envelope and Knowledge Delta become the current conceptual boundary; exact fields remain unaccepted until exercised.
- Existing multi-view fixtures and the transitional Claim Schema are historical validation assets, not implementation specifications.
- MVP work starts with an outcome-oriented Design Golden Run, not schema freeze, storage selection or UI construction.
- Model execution paths need not be deterministic; deterministic checks apply only where a concrete validation or persistence need is proven.
- Human-view work continues only with knowledge produced by the same real task.
- DEC-2026-09-02-001 and DEC-2026-09-03-001 remain active. DEC-2026-09-03-002 remains useful downstream guidance but no longer defines the current implementation priority.

## Review Triggers

- Strong models repeatedly fail because they lack a stable investigation method that cannot be expressed as direction, policy or outcome requirements.
- Result Review cannot reliably detect direction or policy failures without inspecting the full execution trace.
- A thin Knowledge Delta loses project facts needed across tasks.
- Companion generation produces low-quality or drifting human material despite a correct Base.
- Provider-neutral contracts prevent use of a materially valuable model-specific capability.
- The governance burden exceeds the cost of the Agent failures it prevents.
