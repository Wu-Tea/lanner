## Context

目标和讨论已经分布于产品说明、架构、调研和多份决定。旧历史日志有 159 行，交接入口包含大量阶段性信息。用户将提供案例，需要先保留可独立恢复的目标状态，避免案例中的内容无意变成新的产品方向。

## Decision

1. 保存案例到来之前的全量对齐快照，区分已确认要求、用户报告、设计提案、资料证据、未知和未完成工作。
2. 可以复写不合适的记录文件；本次先备份原文件，再重写短 handoff 和归档支持的 session-log。旧决策与原历史内容保持可追溯。
3. 后续案例记录其自身来源与 scope，分析发现不自动变成本项目的目标、规范、完成条件或架构决定。
4. 用户明确修订相应目标后，更新正式文档与决定，再生成新的基线版本；本次快照保持其历史含义。

文件名、归档布局和案例记录字段是实现该请求的整理选择，不是用户接受了产品的技术架构或物理 Base。DEC-2026-09-07-003/004 继续为 proposed；“方便传播”等明确要求的确认范围保持原状。

## Reasons

- 完整快照让后续会话无需从案例内容反推原目标。
- 精确的来源、范围和确认状态避免把 Agent 的提案当成用户决定。
- 短交接与有归档的历史便于恢复，备份和哈希保留复核依据。
- 独立案例可以贡献证据，也能明确指出需要由人决定的目标变化。

## Rejected Alternatives

- 只依赖聊天上下文保留当前目标：不能满足用户要求的持久完整记录。
- 把所有已讨论方案一并标记为 accepted：超出本轮授权及此前确认范围。
- 直接把案例内容合并进主目标：失去案例范围和目标变更的可追溯性。
- 复写后丢弃旧记录：没有必要，且会损失演变理由和复核来源。

## Consequences

- 本轮完成资料和上下文维护，不启动安装、应用开发或 Golden Run。
- `handoff.md` 保留当前目标与唯一下一动作；`session-log.md` 保留历史入口和关键里程碑；基线是固定时点快照。
- 案例分析使用自己的记录位置，发现先标明证据和适用范围。普通案例调查与记录可以自主推进。
- 需要改变目标时精确确认变化命题；用户已给出的明确新指令可以直接构成授权，不额外重复请求。

## Review Triggers

- 用户明确改变目标、范围、规范、验收或实施阶段。
- 案例证据揭示基线遗漏、误记或先前推断不成立。
- 新版本基线形成，或案例记录方式增加不必要的维护负担。
