## 2. 项目为什么存在

Project Cognition 帮助持续使用 Agent 开发和维护项目的人，让 Agent 围绕真实目标和项目规范工作，让维护者能核验结果、掌握重要决定，并让项目知识在后续开发和人的理解中持续发挥作用。

用户希望无需反复解释项目背景、提醒已存在的工具、重复过去的失败路径，或靠自己不断整理记忆文件。首次接入项目也需要直接调查和建模，不能等开发了很多轮之后才逐渐积累一个可用起点。

`agent-context-sync` 是这个想法的早期雏形。用户表示，最初方向模糊，近期积累的 Agent 使用经验让目标逐步清晰。因此原 Skill 是应保留价值并超越的实际基线；新产品还要与已有成熟方案比较，不能预设自建一定更好。

主要使用者是把 Agent 用于长期项目开发和维护的人，以及接续工作的 Agent。人关心当前目标、交付依据、关键取舍、项目行为与改动影响；Agent 需要相关事实、规范、能力、经验、决定和未知。

## 4. 六项期望能力

PC-G0–PC-G5 是文档导读编号。目标的来源见上表，以下产物与完成边界细化来自当前设计文档，尚未全部得到单独确认。完整规格见 [能力目标](../../docs/product/capability-goals.md) 与 [MVP](../../docs/product/mvp-spec.md)。

### PC-G0：第一次接入就能建立项目模型

- 输入：用户指定的项目及可访问的源码、配置、构建、测试、文档与决定；不依赖已有会话或工具记忆。
- 结果：项目用途与运行边界、主要模块职责、依赖和接口、关键业务/数据/事件路径、工具能力、规范、风险和未知，保留来源与适用 revision。
- 覆盖：调查整个指定项目的第一方模块和影响行为的材料，明确已调查、仅定位、未完成与排除范围及原因。目录枚举不能等同于语义理解。
- 大项目可分段完成和接续，局部完成时保留整体剩余范围。不能用一份目录树或概述冒充完整建模。
- 从零项目先形成目标、约束与设计模型，再随代码出现补充实现事实；这一分支的交互细节仍为提案。
- Agent 自主选择调查方式。全项目建模是产品能力，不要求自建理解所有语言的解析器，也不要求长期复制每个符号或全部关系。

### PC-G1：任务方向和重要变化始终清楚

- 接受普通语言任务，保留原请求；必要时用简短 Task Frame 呈现目标、scope、完成条件、相关规范和人类决策点。
- 会实质改变目标、范围或完成条件的解释需要让用户看见；临时方案不能悄悄替代原需求。
- Agent 自主调查、规划、实现和验证。普通局部任务保持简短，结构性任务使用与影响相称的设计材料。

### PC-G2：开发中及时使用相关知识和已有能力

- 任务开始及重要变化时，找到当前需要的事实、规范、决定、能力、踩坑经验、研发路径和未知项。
- 用户只描述用途，也应有机会找到未点名的已有工具；提示用途、入口、适用条件、来源和限制。
- Agent 核实后决定复用、适配或新建。检索为空不能证明能力不存在，过期或不适用的经验不能强制复用。
- 目标/方案变化、准备新增能力、进入新模块和相关失败是拟覆盖时机；事件、语义判断和检索的具体配合未定。
- 只提供当前有用的内容，避免反复读整份历史。已保存、已检索、已送达、已查阅、已核实、已用于选择是不同状态。

### PC-G3：交付有依据，人能判断接受或返工

- 交付回答原目标，说明规范遵守、产物、证据、影响范围和未知。
- 重要完成条件对应实际产物或执行证据，给出核验方法及满足、未满足或尚未验证的判断。
- 证据与结论风险相称；全局结论同时说明调查范围和盲区，测试/运行证据绑定版本与环境。
- Agent 自评、证据核验、独立评审、用户接受和长期知识准入各自记录。一次测试通过不能代替整个目标满足。

### PC-G4：中途及时捕获，长期知识可靠可更新

- 新能力、验证过的修复、方案试验、明确纠正、来源变化和重要未知可在任务结束前形成候选。
- 先保存必要观察；尚未证明的原因保持推断或待查。研发路径保留尝试、结果和重要取舍，不保存完整内部推理。
- Task Result 服务当前工作；Knowledge Delta 提出长期候选；Promotion 根据来源、scope、冲突、状态和必要确认决定 Base 更新。
- Base 保留跨任务有价值的稳定事实、关系、决定、风险和重要未知；临时信息不默认长期保存。
- 依赖、影响或证据变化触发适用性复核，冲突与替代保留历史。换会话仍能找到当前目标、未解决问题和待整理候选。

### PC-G5：帮助人理解项目并作维护判断

- 使用通过准入的同一 Base，围绕“项目怎么运行”“为什么这样设计”“改这里影响哪里”等问题生成资料。
- 从用途、输入输出和完整行为开始，再引入内部名词；文章、框架图、流程、模块细节、关系和证据按读者问题选择。
- 支持总体到细节、保持当前关注对象、查看证据并返回原位置；不要求每个任务生成全部视图。
- 同一对象和关系在不同资料中保留语义身份与来源，布局、缩放等只是交互状态。
- 资料生成成功和真正帮助读者完成判断分别验证；资料中的语义修改先作为知识变更处理。

## 5. 贯穿所有能力的规则

稳定维护四件事：`direction`（方向）、`policy`（相关规范）、`outcome`（结果要求）、`knowledge promotion`（知识准入）。调查深度、工具、规划、推理和呈现方式由 Agent 自主选择；新增过程约束要有真实失败和成本依据。

知识种类保留 derived fact、declared intent、observed evidence、inferred explanation、ephemeral context 的区别。来源与生命周期使用 observed、inferred、proposed、human-confirmed、superseded 等状态表达；不是强制把多个维度压成一个枚举。

- 代码和配置支持实现事实；业务原因和架构取舍由已确认决定支持；测试和运行结论受 revision 与环境限制。
- 每项推断标为 inferred；每项人工确认绑定准确命题与 scope。采纳候选不自动把其内容标成人工确认。
- 冲突同时比较主题、scope、值、authority 与替代关系；过期通过依赖、影响和证据变化判断。
- 人负责目标、规范、重要架构取舍和风险接受；已有授权持续有效，避免为相同事项反复确认。
- Base、任务结果、交接、会话历史、决策与人类资料各有职责。`.agent-context/` 是本项目接续机制，不是已经选定的产品知识存储方案。
- 长期记录避开 secrets、凭据、完整私人对话和无关个人信息。自动捕获不扩大授权范围。

具体语义由 [Base 契约](../../docs/contracts/base-knowledge-contract.md)、[Agent 结果契约](../../docs/contracts/agent-output-contract.md)、[知识契约](../../docs/contracts/knowledge-contract.md)、[资料所有权](../../docs/contracts/projection-ownership-contract.md) 和 [人类资料契约](../../docs/contracts/visual-view-contract.md) 保存。

## 6. 当前候选架构与产品形态

这是 proposed 的职责分配，不是已批准的技术栈或运行实现：

| 责任 | 候选承担方式 | 尚未冻结的部分 |
| --- | --- | --- |
| 首次调查、建模、相关性与适用性判断 | 现有 Coding Agent，辅以可复用方法 | Skill 数量、具体调查流程和辅助工具 |
| 当前方向与规范选择 | Task Frame、上下文选择、少量规则/Skill | 字段、呈现方式和执行深度 |
| 关键时机读取和捕获 | 宿主事件适配、Hook、工具结果与 Agent 语义检查点 | 事件覆盖、同步/异步策略、故障行为 |
| 知识查询、候选保存与生命周期 | 随包提供或按需调用的知识核心 | 语言、常驻与否、物理存储和索引 |
| 结果与准入校验 | 确定性程序、Agent 评审及必要的人类决定 | 校验条件、评审模型和门槛 |
| 方便传播和接入 | 优先考察一个插件统一分发、分别适配宿主 | 首发宿主、市场、发布方式和版本兼容 |
| 人类理解与决定 | 同源资料及查看/查证/确认入口 | 独立窗口、宿主内界面或文件等形式 |

用户明确要求方便传播，并建议参考 Superpowers 与热门轻量插件。当前建议是：用户安装一个插件，在原来的 Agent 中接入项目；内部少量 Skill 配合运行代码，项目知识独立于插件安装目录维护。此建议未被单独确认。

安装、启用、实际自动能力可用和知识正确使用分别检验。拟定体验还包括集中处理必要依赖与信任步骤、普通语言首次建模、日常按需提供知识、更新不覆盖知识、停用可恢复与导出、与既有工具共存。不能由这些逻辑职责推出用户必须另装数据库、部署常驻服务或使用另一个开发环境。

关于“保证 Agent 按能力和规范执行”，当前区分：

1. 程序可在受控接口和路径内核对查询、送达、保存及状态条件，例如缺少必需证据时不标为已验收。
2. 是否找全相关知识、理解正确、实际采用适用经验与命中业务目标，仍需语义判断、任务证据和效果比较。
3. 目标、规范和风险等人类决定沿明确授权处理；自动捕获候选不等于自动确认。

宿主文档已核对，当前机器上的版本、入口和工具覆盖未运行验证。Hook 或 MCP 不提供全路径保证；具体不可用或故障要显式可见。自有任务入口只在现有接入方式无法满足必要控制点时作为候选，尚未决定自建。

详见 [逻辑架构](../../docs/architecture/information-system-architecture.md)、[产品形态提案](../decisions/DEC-2026-09-07-004-product-form-and-execution-guarantees.md)、[插件调研](../../docs/research/plugin-distribution-and-runtime-patterns.md)。

## 8. 已知真实痛点与案例状态

用户报告 `agent-context-sync` 在开发期间较少读取踩坑经验、研发路径，能够触发记录的场景也较少。具体例子是此前要求的“mouse 的覆盖、转写工具”不会被提醒为项目已有的隐藏能力。

这是用户报告。此前仅在 Project Cognition 的文档、上下文及相关研究/样例材料中定向查找，没有定位该工具的实际实现入口，也没有检查其源项目或原始执行轨迹。因此：

- 工具实际入口、当前状态、具体使用条件未知。
- 不能认定唯一根因是 Skill 描述、Hook 缺失、索引失效或模型不读。
- 后续可区分未记录、未触发、未找到、未送达、未核实及应适用却未使用等环节。
- 此前的 `yolo-study-001` 是历史参考项目；待提供案例的身份未知，不能自动与 mouse 或 yolo 合并。

既有 yolo 参考 revision 为 `dev@9505591f51974c04664d7fc231ddc8685791bcf7`。旧技术说明与多视图 fixture 是资料/交互实验，候选输出诊断任务没有成为已确认需求或已证明缺陷。

## 11. 如何评价成功

必须分别证明三条门槛：保留基线价值并覆盖六项能力；核心任务质量不下降且人工解释、纠偏、查找、核验和维护负担改善；跨会话与项目变化后仍值得持续使用。没有虚构的节省比例或既定成功结论。

比较时使用用户实际的 Agent、agent-context-sync、启动规则和项目约定。固定任务、项目 revision、来源、规范、权限与完成条件；记录模型、环境、上下文与读者学习效应等差异。首次建模成本、后续维护成本和插件接入成本分别统计。

现有验收设计覆盖：

| 案例 | 核对内容 |
| --- | --- |
| GC-001 / GC-002 / GC-003 | 保持原方向、Agent 自主性、识别技术上好但目标错误的结果 |
| GC-004 / GC-005 / GC-006 | 规范、证据强度与全局结论、普通任务轻量路径 |
| GC-007 / GC-008 | 长期准入边界、过期与冲突知识 |
| GC-009 / GC-010 / GC-011 | 人类资料用途、跨模型结果比较、人类决定边界 |
| GC-012 / GC-013 / GC-014 | 依据真实证据评审、后续复用、收益与新增负担 |
| GC-015 / GC-016 | 已有项目首次建模、从零项目设计与事实区分 |
| GC-017 / GC-018 | 未点名隐藏能力的发现和使用、中途捕获及后续复用 |

生成成功、Hook 次数、记忆条数、源码文件数量、插件安装成功或单次任务成功，都只支持各自范围的结论。第一次可行、后续复用、独立运行、真实读者用途和长期成本收益需要各自证据。

## 12. 仍待对齐的内容

1. 六项能力的详细完成条件：初始模型如何达到可用覆盖，开发中哪些选择必须提前得到知识。
2. 关键时机怎样映射到宿主事件、工具结果和 Agent 语义变化；未覆盖和故障如何表现。
3. 如何区分知识送达、核实、正确采用与收益，且不给普通任务增加完整轨迹负担。
4. 现有候选能整体承担哪些责任，哪些差距值得适配或自建；尚未完成公平运行比较。
5. 插件是否成为最终形态；首发宿主与 Windows 支持范围、安装/更新/停用体验与跨宿主兼容。
6. Skill 数量、职责与入口，MCP/CLI/Hook 组合，核心程序是否常驻、存储与索引、语言和模型接口。
7. 哪些知识可按已确认规则准入，哪些必须由人判断，怎样合并提示并处理变更与冲突。
8. 人类资料的首要问题、入口和观察方式；独立应用界面并未选定。
9. 真实试用任务、使用者、比较条件与可接受成本。历史 yolo 候选未确认为下一次实际任务。
10. mouse 工具的真实来源与漏用环节，以及用户即将提供案例的内容、范围和证据。

这些问题开放意味着允许用案例检验方向；不能把未知补写成已决定，也不能因为未实施就退回只总结会话的产品目标。

## 13. 接下来如何处理案例

先按 [案例记录规则](../../docs/cases/README.md) 为实际案例建立独立记录，保留原始问题、来源、revision/环境、可观察事实、用户报告、Agent 推断和未知；注明基于本基线分析。

再说明案例反映哪项能力、支持或挑战什么判断、证据覆盖到哪里。案例中的业务目标、项目规范、工具路径和技术选择有自己的 scope，不会自动成为 Project Cognition 的目标或依赖。

发现涉及产品目标、scope、完成条件、规范或架构取舍的变化，先作为具体修订建议，指向受影响的基线条目和证据。用户明确确认相应命题后更新正式文档并记录理由，再生成新版本基线。普通事实核对、补证和案例记录可直接推进，不新增无必要的确认。

案例可能揭示真实遗漏或推翻先前推断，必须如实报告。保护目标信息的作用是保持来源、范围和变更过程清楚，不是拒绝新证据。
