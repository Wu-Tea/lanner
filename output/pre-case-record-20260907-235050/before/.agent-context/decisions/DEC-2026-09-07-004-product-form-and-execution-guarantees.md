## 已核对的资料与证据范围

核对日期为 2026-09-07。以下是官方文档描述，未在用户当前安装的 Codex、Windows 环境或不同入口中运行验证。

- Skill 打包指令、资源和可选脚本；全文通常在显式调用或 Agent 根据描述选择后加载。因此，单靠安装 Skill 不能证明某个开发时机已执行其中的步骤。[Build skills](https://learn.chatgpt.com/docs/build-skills)
- Codex Hook 提供任务提交、工具调用前后、会话及结束等事件，部分事件可补充上下文或阻止支持的操作。但部分工具路径不受 Hook 覆盖；MCP Hook 的服务缺失或错误不会阻止原操作；异步 Hook 不能控制触发它的操作。安装插件也不等于其 Hook 已获得宿主信任。[Hooks](https://learn.chatgpt.com/docs/hooks)
- MCP 连接工具与上下文；把查询和写入工具暴露给 Agent 本身，不构成固定时机的自动调用机制。[Model Context Protocol](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)
- 插件可以打包 Skill、MCP 服务及 Hook，适合统一安装和分发。各宿主入口支持范围不同。[Plugins](https://learn.chatgpt.com/docs/plugins)
- App Server 为自有产品提供会话、审批和事件流集成接口，是需要自有入口时的候选。接口存在本身不能证明所有动作均可拦截，也不能替代对成熟度和实际覆盖的核验。[Codex App Server](https://learn.chatgpt.com/docs/app-server)

## 候选责任分配

建议把产品视为带运行能力的项目知识应用：优先以插件接入现有 Agent，内部保留可替换的知识核心与宿主适配，以及少量可复用 Skill。插件是交付形式；Skill 数量由职责清晰程度决定。下表是逻辑责任，不要求拆成多个服务或另建一个开发环境。

| 责任 | 主要承担者 | 可观察的结果 |
| --- | --- | --- |
| 首次全项目调查、理解关系、判断经验是否适用 | Agent，使用建模和调查方法 | 初始模型、来源、覆盖与未知；已有事实与设计意图区分 |
| 稳定的项目原则与任务方法 | 项目规则、少量 Skill | 当前相关规范与任务方向清楚；方法允许 Agent 自主选择 |
| 在已支持的关键时机发起读取和捕获 | 宿主事件适配、同步或异步处理程序 | 事件是否出现、处理是否执行、结果是否送达分别可查 |
| 选择相关能力、经验、研发路径与规范 | 知识核心调用检索与必要的语义判断 | 精简的相关内容、来源、适用范围与未覆盖部分 |
| 保存知识及其来源、版本和准入状态 | 知识核心及其写入接口 | 候选、已准入内容和被替代内容可区分；状态变更有依据 |
| 检查结果和知识准入条件 | 程序校验、Agent 语义评审、必要的人类决定 | 明确哪些条件满足、未满足或未验证；结论与证据绑定 |
| 帮助人理解项目、查看差异和作出决定 | 同一 Base 的资料与交互入口 | 能定位相关解释、证据和待决定事项 |

MCP 或 CLI 可以提供知识核心的调用接口。核心是否常驻、怎样存储、界面放在何处，继续由实际需求决定。运行代码也可以随插件或 Skill 打包；可靠性应归因于谁实际调用和校验代码，而非所在目录名称。

## 保障范围

1. **可以用程序保证的条件，限定在受控路径内。** 例如进入任务模型请求之前确实执行了知识查询、将查询结果交给宿主、保存了候选记录；产品自己的完成或准入接口在必要证据或确认缺失时不改变状态。程序还需验证执行成功与失败状态，不能用 Agent 自报“已读取”代替证据。
2. **需要语义判断与效果验证的结果。** 包括查询是否找全、Agent 是否理解并采用正确经验、方案是否符合业务目的、初始建模是否遗漏关键关系。提供资料不能证明使用正确，评审通过也不是绝对正确的证明。用具体任务中的选择、产物和后续复用评估。
3. **需要明确人类决定的事项。** 目标或 scope 的实质变化、项目规范、架构取舍和风险接受，沿已确认的授权边界处理。已有有效授权不重复询问，捕获候选不等于自动获得确认。

规则按性质落到不同机制：可机器判定的规则由校验器处理；语义规则由上下文、评审和证据支持；人类决策规则由确认状态控制。资料以带来源的数据提供，未经确认的经验不能因注入上下文而变成项目规范。

事件接入必须显式说明宿主版本、入口、支持的工具路径、信任与启用状态、失败行为和送达时机。若某个检查不受当前接入控制，应显示未覆盖或未验证；不能因为 Skill 写了“必须”就标为已保障。

## mouse 示例中的预期行为

以下是验收设想。当前尚未定位用户所指 mouse 工具的真实入口或原始执行记录。

在工具真实存在、可用且已纳入项目模型的条件下，用户提出有关覆盖、转写的需求，任务提交时先执行能力检索，将匹配能力的用途、入口、限制和证据提供给 Agent。Agent 核对是否适用，再决定复用、扩展或新建。即使用户没有说出工具名称，也应能按用途找到候选。

任务中进入新的模块、遇到相关失败或出现能力变化时，在可观察的事件上再次选择相关内容。宿主不能直接观察的语义变化由 Agent 报告，并明确其可靠性依赖。重要观察及时保存，有跨任务价值的内容形成候选；完成前核对遗漏，准入再沿既有规则处理。

评估至少区分：未记录、未触发、未找到、未送达、未核实、判断不适用、应适用却未使用。检索为空不能推出项目中没有该能力；也不能强制复用过期或不适用的工具。

## 形态比较与取舍

| 候选 | 可以承担的范围 | 代价与限制 | 当前建议 |
| --- | --- | --- | --- |
| 单个或少量 Skill，主要依靠 Agent 主动执行 | 方法整理、能力验证、轻量手动使用 | 中途触发与完成状态容易继续依赖模型遵守约定 | 作为产品内部方法；不独自承担自动发生的承诺 |
| 插件接入现有 Agent，包含运行代码和知识核心 | 提供知识、利用宿主事件、记录与校验、统一安装 | 需要实测不同入口与失败路径；宿主覆盖之外的动作不受其保障 | 优先核验的形态，尚未采纳或安装 |
| 自有任务入口接入现有 Agent 运行接口 | 可以控制自己发起的任务、上下文准备和产品状态流程 | 多一个入口及维护成本；仍需核验运行接口与动作覆盖 | 当必需控制点在插件方式下无法满足时再考虑 |

增加 Skill 数量不能补足缺失的宿主事件。增加独立窗口也不会自动获得控制权。是否引入自有入口，应由具体必需条件及其无法覆盖的证据决定。

## 后续设计与验证问题

先把 PC-G0–PC-G5 逐项映射到触发时机、执行责任、成功证据、失败行为和人工决策点；优先说明知识在关键选择之前如何送达，以及完成与准入状态由谁决定。该责任分配保持薄治理原则，不规定 Agent 的每一步调查或推理。

获得新的实施指令后，才在选定宿主与版本中验证事件和工具覆盖，并用 GC-015–018 等真实案例比较首次建模、隐藏能力使用、中途捕获、后续复用及时间和维护成本。需包含知识缺失、错误匹配、服务不可用、Hook 未启用或不覆盖的情形。文档核对不等于运行验证，机制有效不等于已经优于 agent-context-sync。
