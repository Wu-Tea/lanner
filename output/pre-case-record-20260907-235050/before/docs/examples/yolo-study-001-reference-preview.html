游戏画面如何变成虚拟手柄输入

yolo-study-001 是一个运行在 Windows 上的游戏手柄辅助程序。它读取物理手柄和游戏画面， 根据画面中的目标生成右摇杆控制量，再把物理输入、辅助瞄准、自动开火和后坐力补偿合成为一份虚拟手柄状态。 游戏最终接收到的是这份虚拟手柄状态。

1. 程序完成的工作

程序运行时持续处理三类输入：物理手柄的当前状态、从游戏窗口取得的画面，以及启动时解析出的配置。 每轮控制更新都会产生一份完整的 Xbox 360 手柄状态，并通过 ViGEm （在 Windows 中创建虚拟手柄的驱动接口）交给系统。

1.1 三类输入

物理手柄
摇杆、扳机和按键的当前值。未被辅助逻辑改写的部分会继续传入最终输出。
游戏画面
程序通过 DXGI 取得屏幕中央区域，随后用 GPU 模型找出人物或提示区域。DXGI 是 Windows 的图形捕获接口。
运行配置
包括捕获尺寸、模型文件、视觉频率、控制器频率、输出开关和安全策略。配置可能来自代码默认值、配置文件、环境变量和命令行。

1.2 一份输出

输出包含左右摇杆、扳机、肩键、方向键等完整状态。项目使用 ViGEm 创建一个虚拟 Xbox 360 手柄； 对游戏而言，这个虚拟设备和普通手柄使用相同的输入格式。辅助瞄准主要影响右摇杆，自动开火影响指定的开火键， 后坐力模块在右摇杆结果上增加补偿量。

1.3 默认启动入口

常规手柄启动从 scripts\launch\gamepad_start.bat 开始。未设置 GAMEPAD_RUNTIME 时，脚本进入 native 分支并调用 gamepad_native_cpp_start.bat，后者启动 cod_native_runtime.exe。 Python 路径需要显式选择。 

scripts\launch\gamepad_start.bat
  → scripts\launch\gamepad_native_cpp_start.bat
  → native\vision_native\build\Release\cod_native_runtime.exe

2. 一次控制更新如何完成

原生进程通过高频循环更新手柄。循环的一次迭代称为一个控制 tick。 仓库示例配置把控制 tick 设为 1000 Hz，把活跃视觉捕获设为 160 Hz。 两个频率不同，因此若干控制 tick 会共享最近一次已接收的视觉结果。

一次 tick 按以下顺序执行：

  1. 读取物理手柄，保存本轮会用到的按键和摇杆值。
  2. 检查视觉服务是否发布了新的画面处理结果。
  3. 新结果通过帧编号、捕获时间和新鲜度检查后进入目标协调器。
  4. 目标协调器根据画面证据和手柄意图生成一份 TargetPlan。
  5. 控制器根据计划选择瞄准键按下后的目标获取（ADS Acquire）、已建立目标后的身体跟随（BodyLock Follow）或手动模式，并计算右摇杆候选值。
  6. 状态机决定本轮采用手动值还是 AI 候选值；输出合成器随后加入自动开火、后坐力和辅助方向键。
  7. 完整状态通过 ViGEm 更新虚拟手柄；遥测与 Fusion 发布在交付之后执行。

3. 视觉结果进入控制链的条件

画面识别由 VisionEngine 完成。它用 DXGI 取得屏幕区域，用 CUDA 在 GPU 上准备模型输入， 再用 TensorRT 执行固定尺寸的模型。结果包含目标位置、证据类型、帧编号和各阶段耗时。

3.1 最新结果的发布

VisionService 只暴露最近一次快照。控制循环取得快照后， VisionDeliveryGate 检查该结果是否来自新的源帧、帧编号是否前进、捕获时间是否足够近。 通过检查的结果才会进入目标协调器。选择代次（selector generation）是目标选择器为一次连续选择周期分配的标识， 后文用它判断提示证据是否仍属于当前目标。

3.2 “没有新帧”和“新帧没有目标”

这两个状态对控制链的含义不同：

发生的情况目标选择是否更新控制链处理
控制 tick 到达，视觉尚未产生下一帧不更新继续使用上一份由源帧产生的不可变计划，不伪造新的检测结果，也不续期目标控制权。
视觉产生新帧，新帧中没有选中目标更新为空立即清除通用目标控制权；只有当前同代且仍可见的提示像素能够提供有限的 aim-only 延续。

时间例子

源帧 101 识别到一个目标并生成计划 P101。接下来的几个控制 tick 尚未收到源帧 102， 因而继续根据 P101 更新手柄。源帧 102 到达后若没有目标，控制链会处理“新的无目标证据”， 而不会把 P101 当成刚刚重新识别出的目标。

associated_weak

4. 目标身份与控制模式

检测结果会随画面变化而移动、消失或出现多个候选。TargetCoordinator 把当前证据整理成一份 TargetPlan，供本轮以及后续尚未取得新视觉帧的控制 tick 使用。

4.1 TargetPlan 保存的内容

计划至少回答以下问题：

  • 当前目标对应哪个选择代次和源帧；
  • 目标处于获取、跟随、交接或清除中的哪个生命周期阶段；
  • 期望瞄准点与画面中心相差多少；
  • 当前视觉证据允许瞄准、开火或仅允许有限延续；
  • 这一轮采用手动、ADS 获取还是 BodyLock 跟随。

4.2 三种控制模式

模式使用场景本轮结果
Manual没有可用目标计划，或辅助逻辑没有获得输出权限。右摇杆保持手动控制。
AdsAcquire玩家进入瞄准状态，需要把视角移动到当前计划的目标点。ADS 控制器生成一份目标相对的右摇杆候选值。
BodyLockFollow已建立跟随关系，需要持续跟随目标身体位置。BodyLock 控制器生成一份目标相对的右摇杆候选值。

ADS 与 BodyLock 在同一个 tick 中走互斥分支。选中的候选值经过一次 AimDynamicsShaper，用于限制和整理动态响应。随后 AssistControlStateMachine 根据 Manual、Capture、Track 和 HandoverSeek 状态， 形成尚未叠加后坐力补偿的右摇杆值，代码中称为补偿前右摇杆（pre-recoil stick）。

4.3 为什么历史实现会出现粘滞与回弹

旧的低帧率路径曾同时保存目标、预测位置、前一输出和多组超时状态。多个层次会先后修改同一个右摇杆值， 并各自决定何时保留或释放。仓库记录的症状包括目标交接粘滞、新旧帧切换回弹、停止后延迟释放、 同方向放大和手动输入受抑制。

2026-08-10 的清理移除了通用目标保留（target hold）、检测结果外推（detector projection）、 旧的选择后增强、多套手动意图仲裁、待定输出和重复输出校验路径。当前代码把目标身份放在 TargetCoordinator，把手动/AI 输出权放在 AssistControlStateMachine，使故障可以回到明确的状态维护位置。

5. 最终手柄状态的形成

控制状态机输出补偿前右摇杆值。OutputComposer 随后以物理手柄快照为起点， 按固定阶段加入这份右摇杆值和其他控制结果，形成交给游戏的完整手柄状态。

5.1 开火

玩家按下的物理开火键始终属于物理透传。AutoFireGate 只负责程序生成的开火贡献， 并要求当前证据和开火区条件满足安全策略。弱视觉证据与提示延续不会获得自动开火权限。

5.2 后坐力

后坐力模块在补偿前右摇杆值之后追加预先计算的补偿量，代码中称为前馈（feed-forward）。 它使用自己的参数预设（profile）、校准和备用处理（fallback）， 但不会选择目标，也不会延长目标生命周期。排查“瞄准方向正确但开火后发生稳定偏移”时， 可以把补偿前右摇杆值与后坐力贡献量分开比较。

5.3 交付时点

RuntimeLoop 先确认合成状态已经完成（finalized），再调用 VirtualGamepad::update。遥测、性能摘要和 Fusion 数据发布安排在当前输出交付之后， 这样诊断工作不会成为本轮手柄更新的前置条件。

6. Fusion Canvas 的位置

Fusion Canvas 是一个可选的独立显示进程。它读取 C++ 主运行程序发布的最近一份目标数据， 在屏幕上绘制标记，帮助维护者观察识别与选择结果。

Canvas 接收的数据用于显示。目标选择、瞄准、自动开火和后坐力仍在 C++ 主运行程序中完成。 发布路径只保留最新消息，代码中称为 latest-only。运行时不会等待 Canvas 消费旧消息。

6.1 避免 Canvas 被视觉系统再次捕获

Windows 显示模式变化时，原有的捕获排除证明可能失效。Canvas 会先隐藏窗口，刷新虚拟屏幕几何， 重新设置并读回 WDA_EXCLUDEFROMCAPTURE，再运行 DXGI ROI 捕获探针。 全部检查通过后才恢复显示。检查失败、结果含糊或连续失效时，Canvas 保持隐藏。

这段恢复逻辑源于两次已定位的退出：WM_DISPLAYCHANGE 或 WM_DWMCOMPOSITIONCHANGED 曾被当成永久失去证明，进程随即退出。 现在这两类消息触发重新验证，并记录具体原因。

7. 配置值从哪里取得

仓库中同时存在结构体默认值、提交的示例配置和 README 中的说明。 它们描述的使用范围不同。某次真实运行使用什么值，需要查看该次启动完成全部覆盖后得到的最终配置， 运行时称其为最终生效配置（effective config）。

7.1 加载顺序

  1. RuntimeConfig 先用 C++ 结构体默认值初始化。
  2. 运行时读取指定配置文件；未指定路径时尝试根目录 config.toml。
  3. 命令行提供运行参数预设（profile）时采用该预设；否则读取配置文件中的 [runtime].profile。
  4. 配置文件中的其他键依次覆盖 profile 产生的值。
  5. 受支持的环境变量覆盖相应配置。
  6. --capture-fps、--auto-fire-output 等独立命令行参数最后应用。
  7. 配置通过范围与几何校验后进入运行时；来源记录在 effective_sources 中。

可执行程序支持 --dump-effective-config。该输出包含捕获尺寸、tensor 尺寸、 模型路径、调度频率以及配置、模型、可执行文件和控制契约的来源校验哈希。

8. 常见现象从哪里开始排查

下表把用户可观察的现象连接到负责该状态的代码位置。排查时先确认现象在哪个阶段首次出现， 再检查上游输入和本阶段输出。

画面中有人，控制链没有目标
先看 VisionResult 是否产生，再看 VisionDeliveryGate 是否因重复、倒退或过旧而拒绝。随后检查选择结果记录的源帧与控制权限字段。
目标在多人之间频繁跳动
检查选择代次、TargetCoordinator 的身份与生命周期输出，以及手柄是否触发了目标交接意图。
手动输入与辅助瞄准互相拉扯
记录控制器初始候选值、动态成形后的候选值、状态机状态和补偿前右摇杆值。确认发布版本路径中没有新增第二个手动/AI 状态写入位置。
开火时准星出现固定方向偏移
比较补偿前右摇杆值与后坐力贡献量。若偏移在补偿前已经存在，继续回查控制状态机；若只在叠加后坐力补偿后出现，检查后坐力参数预设与校准。
程序有结果，游戏没有响应
检查 OutputComposer 是否进入完成状态、输出顺序校验是否通过、VirtualGamepad::update 是否成功，以及 ViGEm 虚拟设备是否连接。
切换全屏或显示器后 Canvas 消失
读取最新 Fusion 日志中的准确失效原因。Canvas 隐藏期间检查捕获排除是否重新验证、渲染尺寸是否更新，以及 DXGI 捕获证明是否重新建立。
仓库文档与运行参数对不上
使用 --dump-effective-config 取得本次运行值及来源，再分别与示例配置、结构体备用值和 README 的声明范围比较。
