# Base Knowledge Contract

Status: Reset draft 0.1  
Phase: R1 minimal durable knowledge boundary  
Last updated: 2026-09-07

## 1. Purpose

Canonical Base 保存跨任务仍有价值的项目认知，使不同人员、模型和 Session 能在同一组已知事实、规范、决定、风险和未知项上继续工作。

Base 是长期认知锚点，内容范围由首次项目建模和持续任务中的复用价值决定。

### 首次建立 Base

首次全项目调查是一项独立任务：输入可以只有项目源码和已有资料，Base 可以尚不存在。调查先形成初始模型及来源、关系、覆盖和未知，再按相同准入规则建立首个 Base；用户无需等待后续开发任务逐渐凑齐项目全貌。

初始模型和调查报告分别承担长期语义与本次覆盖证据。全项目来源清单、详细阅读记录和完整扫描输出留在任务证据中，Base 保留重要事实、关系、决定、风险、未知及其来源。初始化增量可以比日常更新更大，但仍按复用价值选择。

直接可定位的事实按已授权项目政策记录；推断保留 inferred；业务原因、目标和架构取舍需有相应确认。从零项目先登记已确认意图与明确标记的设计候选，待实现后分别加入观察证据，不能将设计模型标为已实现架构。候选预览与已接纳模型使用各自状态。

## 2. Base Is

- 持久项目知识的唯一当前登记处；
- 项目事实、意图、规范、决定、重要关系、风险和未知项的可追溯索引；
- 后续 Agent 任务选择相关上下文的来源；
- 所有 current 人类资料的语义来源；
- 能保留修正、冲突和 supersede 历史的版本化边界。

## 3. Information Ownership Around The Base

- 源代码、配置和构建文件继续拥有实现内容；
- 测试、运行产物和日志继续拥有绑定条件下的观察；
- ADR 或 decision record 继续拥有人类确认的理由；
- Task Result 继续拥有本次回答和工作过程；
- Base 保存这些来源之间可复用的项目语义、状态、关系和引用；
- 人类资料按读者问题投影 Base 内容。

## 4. Admission Test

一个候选只有同时满足以下条件才值得进入 Base：

1. 后续任务或读者仍可能需要它；
2. 有稳定且可区分的 topic；
3. scope 足以避免误用；
4. 来源或推断依据明确；
5. 当前状态和不确定性可表达；
6. 对现有知识提供新增、修正、冲突、失效或更强证据；
7. 与现有 Base 的冲突已经暴露；
8. 涉及目标、规范、架构取舍或风险接受时已有必要的人类确认；
9. 已完成敏感信息清理，并具有适合长期保留的粒度。

正确但一次性的任务结果由 Task Result 完整承载；Base 聚焦后续仍会复用的部分。

## 5. Minimal Durable Semantics

每项 Base 知识概念上需要回答：

```text
它在说什么？
适用于哪里？
我们怎样知道？
来源能证明什么？
它是观察、推断、提案还是人类确认？
它现在是否仍有效？
什么变化可能要求重新检查？
它修正、冲突或替代了什么？
```

精确字段、枚举和物理格式仍未冻结。

## 6. Knowledge Families

首版表达以下语义；物理实现可以按实际查询和维护需求组合它们：

| Family | Examples |
|---|---|
| Project direction | 产品目标、适用边界、完成条件、读者目标 |
| Policy and invariant | 架构约束、唯一 owner、兼容性规则、验收边界 |
| Project fact | 应用入口、模块职责、接口、配置行为、实际依赖 |
| Reusable capability | 已有工具、脚本、模块能力及用途、入口、适用条件、限制与可用性证据 |
| Relationship and flow | 关键调用、数据流、状态所有权、运行阶段 |
| Decision | 已确认取舍及其权威记录引用 |
| Risk and lesson | 失败模式、技术债、历史原因和防复发规则 |
| Development path | 围绕目标的方案尝试、实际结果、选择或放弃依据、仍待验证事项 |
| Evidence | 源码、Git、测试、运行观察和外部规范的定位 |
| Unknown or conflict | 影响后续决定的重要未知、scope 差异或竞争解释 |

只记录完成真实任务所证明需要的粒度。

### 让能力和经验能够被找到

已有能力的长期记录至少应让后续工作知道：可以解决什么问题、输入输出是什么、实际入口在哪里、适用范围与限制是什么，以及凭什么认为它可用。入口可引用工具、脚本、函数、模块、使用文档或测试；名称/别名只是检索线索。隐藏能力在首次调查或开发中新发现时都可以成为候选，只有用户描述但尚无实现来源时保持待定位状态。

踩坑经验保留症状、发生条件、观察/证据、已证实或尚未证实的原因、尝试结果、适用或不适用边界。研发路径保留目标、方案、可观察试验结果和重要取舍依据；未经确认的原因不能因为被反复提及就升级为事实。内容通过来源与关系关联，避免再建一套与 Base 并行的当前经验库。

## 7. State and Authority

Base membership 表示跨任务价值；human-confirmed 表示人类对特定命题和 scope 的接受。一个有用的架构解释可以作为 `inferred` 进入 Base，并持续展示其推断状态。

至少保留以下独立问题：

- `epistemic`：observed 或 inferred；
- `acceptance`：not-applicable、proposed、human-confirmed 或 rejected；
- `lifecycle`：active、superseded 或 retired；
- `verification`：当前证据是否足够、是否需要重新验证。

首版可以继续验证这些名称，同时保持四个问题在语义上独立。

来源权威按问题类型判断：

- 代码和配置证明某 revision 的实现；
- 测试和运行证据证明绑定条件下的观察；
- 人类决定证明意图和取舍；
- Agent 跨来源解释属于 sourced inference；
- 生成资料不因被写入 Git 就成为权威源。

## 8. Scope

Scope 可以包含 repository、revision、branch、profile、environment、platform 或其他会改变解释的维度。

- 不相交 scope 的不同值可以并存；
- scope 重叠且值不兼容时才进入冲突判断；
- scope 缺失但会改变含义时标记待确认；
- 本地或私有运行值保留其原始 scope；共享项目规范由明确的人类决定产生。

## 9. Knowledge Delta Application

候选可以在开发中发现新能力、验证修复、完成试验、用户纠正或来源变化时形成，不必等最终结果。候选记录要保留实际观察与尚未解决的问题；仅发生一次失败不支持通用原因或修复结论。原始尝试保存在任务证据中，跨任务有用的部分才参与准入。

每次任务可以提出：

- `add`：新增可复用知识；
- `revise`：修正现有知识；
- `contradict`：记录竞争值或解释；
- `mark-stale`：现有知识需要重新验证；
- `supersede`：以新知识替代旧知识并保留历史。

应用 Delta 时必须：

- 知道它基于哪个可见 Base 状态；
- 比较 stable topic、scope 和来源；
- 防止旧任务静默覆盖新知识；
- 对受保护内容请求人类确认；
- 保留必要的历史和审计引用。

首版可以人工完成这些步骤，不因此假设已经需要事务数据库。

## 10. Human Confirmation Boundary

以下内容默认需要明确人类确认：

- 产品目标和完成标准；
- 规范性项目规则和架构不变量；
- 技术或架构取舍的理由；
- 业务语义、用户验收和风险接受；
- 退休主要路径或替换唯一状态所有者；
- 解决两个都合理的 intent 冲突。

直接可定位的实现事实、测试结果和重新生成的投影可以按项目策略自动记录，但必须保留 scope 和来源。

## 11. Base Revisions

Base 需要逻辑上的 revision，使 Agent 和人知道一次结果读取的知识基础。物理实现可以是 Git、文件快照、事件日志或数据库。

- 一次 accepted Delta 产生新的逻辑 revision；
- 修改保留旧值或 supersede 链接；
- 并发候选通过 revision 比较暴露重叠变化和冲突；
- 投影失败不改变已经接受的 Base 内容；
- Base revision 不等于仓库 Git commit，但应能引用相关 commit。

## 12. Retrieval

Agent 默认只读取：

1. 当前任务相关的目标和规范；
2. 直接相关的事实、决定、风险和未知项；
3. 必要的关系和证据定位；
4. 需要时才读取历史和更深来源。

读取不仅发生在任务开始。目标或方案变化、准备新增能力、进入新模块以及相关失败出现时，应重新选择与当前决策有关的已有能力、经验和研发路径。查询可以从需求语义、输入输出、模块、错误特征和项目关系进入，不能只依赖 handoff 已经点名的文件。

提供知识时附相关原因、入口、scope、状态与必要来源，让 Agent 复核后决定如何使用。未找到与项目不存在分别表达；过期或不适用的知识标明限制，不强制复用。检索、提供、查阅与采用的状态留在当前任务证据中；只有确有长期价值的使用反馈再形成 Delta。

检索可以由强模型直接完成，也可以在规模证明需要后增加确定性索引。首版不以向量数据库或完整图查询为前提。

## 13. Human Projection Boundary

- current 资料只使用已进入 Base 的内容；
- 候选 Delta 只能生成明确标记的 preview；
- 一个事实在多种资料中保持同一身份、scope 和来源；
- 人类资料可删除、重建或更换格式而不损失 Base；
- 人工编辑资料产生的新语义形成新的 Delta，经确认后更新 Base。

## 14. Retention and Privacy

保留：

- 解释当前状态所需的旧 revision；
- 已确认决定和重要 rejected alternative；
- 能防止重复错误的风险和 lesson；
- 支撑长期知识的最小证据摘要和定位。

其他信息继续由其原始系统承载：凭据由安全存储管理，私人对话留在授权会话，完整日志留在证据系统，中间推理和临时探索留在任务上下文，页面状态留在用户会话。

## 15. Base Health Conditions

Base 持续满足以下条件：

- 维护成本低于它为后续任务节省的调查和沟通成本；
- 每条记录增加跨任务价值，而非重复源码或完整回答；
- 关系由真实任务需要和证据产生；
- 数据结构允许更强模型减少字段和步骤；
- 人类能够识别观察、推断、提案和确认；
- 所有人类资料共享 Base 当前语义并可重新生成。

## 16. Open Decisions

1. 首个 Base 的最小物理形式。
2. Knowledge Delta 的审阅和提交粒度。
3. 哪些 observed fact 可以按策略自动晋升。
4. Base revision 与 Git revision 的关联方式。
5. 哪种规模和查询频率会证明确定性索引比 Agent 直接选择上下文更有价值。
