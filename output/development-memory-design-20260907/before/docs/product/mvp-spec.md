# Project Cognition MVP Spec

Status: Product and validation design; effectiveness unverified  
Phase: R1 materials, direction and architecture review  
Last updated: 2026-09-07  
Related decisions: `.agent-context/decisions/DEC-2026-09-03-003-thin-governance-and-companion-knowledge.md`, `.agent-context/decisions/DEC-2026-09-05-001-staged-validation-and-evidence-review.md`, `.agent-context/decisions/DEC-2026-09-07-001-design-first-and-context-sync-baseline.md`

## 1. Outcome

Project Cognition 希望让维护者把真实项目工作交给 AI 后，能够核对方向、判断交付，并利用积累下来的知识继续维护项目。维护者的精力应更多用于目标、业务语义和重要取舍，重复解释、纠偏和复核的负担应当逐步减少。

用户要求新应用比 `agent-context-sync` 更完善、更好用。能力目标、体验细化和比较门槛集中在 [产品能力目标](capability-goals.md)。本规格负责功能和分阶段验证；当前先整理资料、方向与架构，以下试运行均为后续设计。

产品覆盖“首次接入与初始建模”和“持续开发与知识更新”两个阶段。对于新接入的已有项目，能够从可访问源码与资料直接形成全项目模型；对于从零项目，先形成目标与设计模型，再随实现补充事实。持续工作能力不能替代首次建模的单独验收。

首轮验证一个具体命题：

> 向 Agent 提供正确方向、相关项目规范和结果要求，并让强模型自主完成调查与推理，能否使一次真实项目任务保持目标一致、结果可验证，并把其中有长期价值的认知伴生为对人类友好的项目资料。

一次完整工作提供这条路径的可行性证据，并暴露候选治理边界的缺口。持续可靠、知识长期有用以及收益高于成本，需要后续独立运行、真实复用和适当对照分别提供证据。当前尚未完成首轮验证。

## 2. Two Linked Outcomes

### O1 — Govern Agent Work

- 从普通自然语言中保持用户目标、范围和完成条件；
- 向 Agent 提供本次任务相关的规范、事实、决定和未知项；
- 让 Agent 自主选择仓库调查、工具、验证和表现方式；
- 对最终结果检查方向、规范、证据、影响和不确定性；
- 把必须由人判断的事项清楚交还给人。
- 记录本次需要人补充背景、纠正方向和核验结果的实际工作，为后续判断收益提供依据。

### O2 — Produce Companion Human Knowledge

- 从真实任务结果中识别可复用知识增量；
- 只将通过证据、冲突和确认边界的内容晋升到 Canonical Base；
- 从同一 Base 按人的问题生成低负担资料；
- 让维护者或新成员能借助资料找到影响范围、关键未知和待决定事项；
- 保证文章、框架、流程、模块和关系视图不形成多套当前事实。

O1 是当前主线，O2 使用 O1 的真实产物同步验证。资料生成、读者使用和后续 Agent 复用分别记录结果；人类理解效果属于待验证目标。

首次全项目调查与建模本身也是实际项目任务，能够同时提供 O1 的可核验结果和 O2 的初始知识。它不依赖此前已经发生多轮开发。

## 3. Users

### Maintainer

对产品、架构、风险和最终结果负责，需要看清本次改变了什么、依据是什么、哪些选择仍由自己决定，并能利用留下的知识继续维护项目。

### Coding Agent

需要在一次任务中获得足够但不过量的项目上下文，并能自由使用自身能力和仓库工具。

### Reader or New Contributor

需要从项目用途和真实行为出发，逐步理解结构、流程、模块、关系和证据，再据此完成一个与自身经验相称的维护判断。

## 4. Product Boundary

### The System Provides

- `Direction`：目的、适用边界、完成条件和需要人决定的事项；
- `Policy`：与当前任务相关、已经确认的项目规范；
- `Outcome`：结果必须回答什么、提供什么证据、暴露什么未知；
- `Promotion`：哪些知识进入 Base，以及确认、冲突和生命周期边界；
- `Projection ownership`：所有人类资料从同一 Base 派生。

### The Model Performs

- 如何理解仓库和选择调查路径；
- 使用搜索、Git、编译器、测试、语言服务或其他工具；
- 是否扩大或收缩调查范围并说明理由；
- 如何推理、交叉验证、画图和组织当前回答；
- 根据模型能力选择合适的工作深度。

### Current Validation Scope

当前阶段交付资料、方向和逻辑架构，审阅完成后再依据新的实施指令进入试用。后续纵向路径包括自然语言目标、相关规范、Agent 自主工作、结果评审、Knowledge Delta 和两种人类资料；实现形态由观察到的确定性校验、持久化、集成和触发需求决定。

## 5. MVP Vertical Slice

首次接入路径为：

```text
指定项目或提供从零项目的目标
→ 确定项目范围与可访问来源
→ Agent 全项目调查，或梳理目标与设计
→ 初始模型 + 来源关系 + 覆盖与未知
→ 核验建模结果，按准入规则建立初始 Base
→ 提供人和 Agent 的共同项目入口
→ 后续任务验证模型是否可用，并按变化更新
```

初始模型的内容和调查边界见 [PC-G0](capability-goals.md#首次接入的两种起点)。模型草稿、已接纳知识和真实使用分别记录状态。后续试用可分段核验这条路径，当前没有运行承诺。

持续工作路径的既有 Design 候选同时检查：

```text
自然语言 Design 任务
→ Task Frame
→ 相关项目上下文
→ 强模型自主选择调查和验证方法
→ Result Envelope
→ Outcome Review
→ Knowledge Delta
→ Promotion Review
→ 按来源、冲突和确认边界接纳最小知识增量
→ 从同一 Base 生成两种互补的人类资料并观察使用结果
```

既有 Design 候选使用固定的 `yolo-study-001/dev@9505591`，旧 fixture 只作证据和对照，其数据结构和 UI 不作为产品实现。新增首次建模案例另在 GC-015、GC-016 定义，不以已有 fixture 或会话总结预填答案。

既有 Design 候选的详细定义见 [Primary Golden Run](../validation/golden-cases.md#2-primary-golden-run)。进入试用前根据能力目标选择并固定实际案例、相关规范、人类决定和完成条件；各候选仍保持提案状态。调查方法由 Agent 自主选择。

该候选运行的交付为 Design 分析、可评审建议及验证计划，代码实施和真实运行接受按各自任务另行判断。两种资料是该实验用于验证同源表达的安排；普通任务按实际需要选择资料数量，也可以没有知识更新。

## 6. Minimal Information Boundary

### Task Frame

概念上至少表达：

- 原始用户请求；
- 本次目标和完成条件；
- scope 与适用边界；
- 相关项目规范和已确认决定；
- 结果最低要求；
- 需要人类决定的事项。

Task Frame 可以由 Agent 从自然语言中生成；用户能够看到并核对所有会实质改变目标的解释。

### Result Envelope

概念上至少表达：

- 对当前任务的直接结论；
- 关键证据和适用范围；
- 对项目约束的遵守情况；
- 影响、风险和替代方案；
- 不确定项、未检查部分和需要人类回答的问题；
- 重要完成条件逐项对应的证据、核验状态和理由；
- 谁进行了自查、证据核验或人工接受，以及尚未核验的部分；
- Knowledge Delta 候选。

结果结构只统一语义，各类任务可以使用最适合当前读者的版式。

### Knowledge Delta

只包含可能跨任务复用的新增、修正、冲突、失效或待确认知识。任务回答、临时调试记录、完整工具输出和中间推理默认不进入 Delta。

## 7. Functional Requirements

### F0 — Initialize a Project Model

- 用户可以将“完整调查并建立这个项目的模型”作为独立任务，无需已有 Base、交接记录或局部开发需求；
- 已有项目的调查范围覆盖整个指定项目，Agent 自主识别技术组成、入口、模块、配置、构建/测试、主要跨模块行为和相关规范；
- 交付有来源与状态的初始知识和关系模型，供人理解、后续 Agent 选择上下文并持续更新；
- 显示实际纳入、排除、已调查和未完成的范围及理由。大项目可分批与接续，部分结果不得冒充全项目完成；
- 关键结构与流程需要对应源码、配置、已有决定或运行证据，源码体现的行为、Agent 解释与人类确认分别保留；
- 沿相同准入规则建立首个 Base，用户集中处理需要人判断的事项；首次建模产生的知识增量可大于普通任务，但不整体保存全部扫描输出；
- 从零项目先记录目标、约束与拟议设计，存在相应实现证据后才表达为实现事实；
- 支持后续按变更范围复核与更新模型；明确局部任务仍走局部路径，不强制每次全项目重扫。

### F1 — Preserve Natural-language Intent

- 用户直接使用自然语言提出任务；
- 系统保留原始请求，并让解释后的目标可比较；
- 发现关键歧义时请求澄清，并让所有影响目标的假设保持可见；
- Agent 可以提出更好的调查方向，但必须标为建议。

### F2 — Select Relevant Context

- 只装配与任务有关的项目事实、规范、决定、风险和未知项；
- Base 不必完整进入模型上下文；
- 来源、scope 和状态随内容一起提供；
- Canonical Base 和人类确认决定拥有长期当前语义；handoff、README 和历史回答分别承担游标、入口和历史职责。

### F3 — Preserve Model Autonomy

- Agent 根据仓库、任务和模型能力选择语言工具、文件顺序、调查深度和推理方式；
- Agent 可以扩大调查范围，但应说明与目标的关系；
- 模型能力提升时，核心契约无需因更好的执行方法而改变；
- 较弱模型需要的额外提示作为可选支持，并保持强模型路径简洁。

### F4 — Review Outcomes

- 检查结果是否回答任务目标和完成条件；
- 检查是否违反相关项目规范；
- 检查关键结论是否有足以支持其强度的证据；
- 按预先明确的完成条件核验实际产物、源码、测试或运行记录，写明满足、不满足或尚未验证及其依据；
- 检查事实、推断、建议和人类决定是否分开；
- 检查影响、未知项和人工决策点是否充分暴露；
- 结果 Review 通过不等于用户验收或 Knowledge Delta 已晋升。

逐项判定、证据核验和总体 Review 状态使用 [结果契约](../contracts/agent-output-contract.md#7-outcome-review)。首例先用少量具体结果校准人工与模型判断；模型自查、人工核验及自动评审的可信程度分别保留，自动评审效果待验证。

### F5 — Scale Evidence With Risk

- 局部低风险任务可以使用轻量证据；
- 结构性变更、全局否定结论和正式 Gate 需要更强的范围与盲区说明；
- “没有发现”保留实际调查范围；“项目中不存在”同时提供与结论强度匹配的覆盖说明；
- 运行时或外部系统无法由静态仓库证明时必须明确限制。
- 按风险引用足以复核关键行为的执行记录；必要的记录包含实际动作及其结果，完整内部推理不属于验收证据要求。

### F6 — Promote Durable Knowledge Deliberately

- Delta 内容只有在跨任务有价值时才成为 Base candidate；
- 每项 candidate 保留来源、scope、状态和必要的未知项；
- 用户目标、架构取舍、规范和风险接受需要明确人类确认；
- Base 更新由 Knowledge Delta、来源、scope、冲突检查和确认状态共同决定；
- 持久化内容聚焦可复用知识，并清理重复、任务局部和敏感信息。

### F7 — Produce Human Material From The Same Base

- 根据人的实际问题选择资料形式，不一次生成全部视图；
- 内容从具体用途、输入输出和完整行为开始，再进入内部机制；
- 相同事实和关系跨资料复用同一 Base 身份和来源；
- 生成资料可以删除并重建，不影响长期知识；
- 人类修改中的语义变更形成新的 Base candidate，确认后重新生成资料。
- 通过一个具体维护问题观察读者能否使用资料，生成成功只记录为产物状态。

### F8 — Remain Provider-neutral

- 核心语义不依赖某个模型名、上下文长度或供应商工具协议；
- 不同模型可以产生不同调查过程和表达；
- 验收比较方向、规范遵守、证据、未知项和结果效用；
- 只有真实能力差异要求时，才增加可选模型配置或降级策略。

## 8. Success Criteria

### Initial Model — First Contact With a Project

首次建模分别验证：无本工具记忆也能开始；整个项目范围有可核对的覆盖记录；主要结构、接口和端到端关系可追溯；重要未知不会被补写为事实；人和后续 Agent 能用模型定位来源并开展新任务。从零项目还要保持目标、设计、实现三种状态的区别。

具体用 [GC-015](../validation/golden-cases.md#19-gc-015--initial-model-of-an-existing-project) 和 [GC-016](../validation/golden-cases.md#20-gc-016--model-a-greenfield-project) 验证。现有 Design 候选通过不能证明首次建模完成，生成初始 Base 也不能证明模型正确或长期有用。

### First Run — Feasibility and Failure Discovery

下列是既有 Design 候选的首轮标准，分别记录任务评审、知识接纳、资料生成和真实读者使用状态：

1. 用户可以核对 Agent 对目标和完成条件的理解，没有关键静默改写。
2. 强模型无需固定扫描步骤即可选择与仓库匹配的调查和验证方式。
3. 结果明确回答 Design 问题，并引用足够证据、scope 和未知项。
4. 在少量明确标为合成的评审样例中，偏离目标、违反规范或缺乏证据的结果会被识别；人工与模型判定分歧有具体记录。
5. 高风险的全局结论会说明覆盖边界；普通局部任务不会被迫提交完整审计包。
6. Knowledge Delta 明显小于任务回答，只保留跨任务有价值的内容。
7. 推断、建议和人类确认不会自动升级。
8. 至少两种人类资料表现来自同一批已确认知识，没有独立维护重复事实。
9. 真实读者能描述项目用途、一次关键行为和一个主要约束，并借助资料定位某项改动的主要影响、一个关键未知和一个待决定事项；只有模型模拟时标为合成评估，真实使用效果保持待验证。
10. 机制数量与真实失败相称；模型已经可靠完成的部分保持由模型负责。

没有真实读者反馈时，可以报告任务和资料生成部分已完成，整体首轮验证保留未完成项。通过首轮也只支持这个任务、revision 和运行条件下的结论。

### Follow-up — Reuse, Repeatability and Cost

后续验证逐步回答：

- **知识复用：** 在新的任务上下文中使用已接纳知识，记录实际帮助了什么、哪些来源仍需复核、哪些知识过期或无用，见 GC-013。
- **独立运行：** 同一模型独立运行或另一个模型完成相同任务，比较结果性质与失败，见 GC-010；一次成功尚不能证明稳定性。
- **收益与成本：** 产品最终需要相对当前 `agent-context-sync` 的条件可比对照，保留相同任务、revision、已知规范及权限边界，见 GC-014 和 [基线比较设计](../research/capability-baseline-and-candidates.md#4-comparison-design)。首轮可行性通过不要求收益实验同时完成；模型、上下文或评审者差异必须说明，结论仅适用于实际比较范围。

首轮按 [运行记录要求](../validation/golden-cases.md#15-evidence-to-record-during-the-first-run) 记录人工补充、纠偏、复核、知识整理和资料使用的工作，以及可获得的耗时与资源数据。缺失项标为未记录，估算注明方法。先观察失败和负担，再制定量化门槛。

## 9. Architecture Health Conditions

MVP 持续满足以下条件：

- 体系聚焦任务方向和结果质量，模型保留调查与推理自由；
- Task Frame 比原始请求更易核对，并忠实保持用户意图；
- 每次任务只保留实际有跨任务价值的内容；无增量时可以不更新 Base；
- 人类资料从 Base 生成并随同一知识更新；
- 模型专用提示保持可选，公共路径保持简洁；
- 工具和 UI 对应已经观察到的确定性需求；
- 治理和复核带来的收益高于其使用成本；这是持续验证目标，结论保留对应的复用或对照证据。

## 10. Work Plan by Task and Function

| Task | Function | Status |
|---|---|---|
| R0 | 确认薄治理与伴生资料双目标 | Accepted |
| R1 | 整理首次建模与持续工作的能力目标、基线、候选和架构，设计完整性与易用性比较 | Current; design only |
| R2 | 新的实施指令后固定真实任务与比较条件，再执行 Design 任务并核验结果 | After design review and instruction to proceed |
| R3 | 根据真实失败缩减或增强契约 | After R2 |
| R4 | 接纳最小知识增量，生成同源资料并观察真实读者使用 | After R3; reader evidence tracked separately |
| R5 | 验证后续任务复用与独立运行，比较相对 agent-context-sync 的完整能力、人工负担与使用意愿 | After R4 |
| R6 | 根据重复缺口选择最小 Skill、Rule、Hook、MCP 或工具 | After validation |

## 11. Open Questions

当前先审阅六项能力、使用要求及责任划分是否准确，重点包含首次全项目建模；具体架构、组件和验收细节仍是设计提案。进入后续试用前再处理以下问题：

1. 首例任务候选是否对应维护者真实需要的变化，哪些行为必须保留？
2. 谁核验首例的关键完成条件，哪些部分可以由模型先做自查？
3. 哪些项目规范必须常驻，哪些应按任务从 Base 选择？
