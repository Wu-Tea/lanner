# 产品能力目标：持续掌握交给 Agent 的项目

状态：产品方向整理，2026-09-07。既有目标与最新用户要求有明确来源；下文的体验细化、比较判据和组件划分为设计提案，尚未经过使用验证。当前工作只整理资料、方向和架构。

## 1. 创建这个应用的目的

Project Cognition 帮助持续使用 Agent 开发和维护项目的人，始终知道：**这次要做成什么、交付是否可信、哪些事要自己决定，以及下次怎样接着做。** 工作中留下的知识同时服务后续 Agent 和人对项目的理解。

首次接入时，应用应主动完成全项目调查并建立初始模型，让用户和 Agent 获得可用的起点；之后通过真实工作持续核实、修正和扩展。首次建模本身就是一项完整的产品功能，不要求用户先积累多轮开发记录。

开发期间，项目知识需要在相关时机主动参与工作：准备实现一种能力时能发现项目已经有什么，遇到问题时能找到适用的踩坑经验与研发记录，新发现又能及时留下。知识的价值要体现为实际选择和行动的改善。

`agent-context-sync` 是这个想法的早期形态，已经解决了项目接续、决策留存和上下文写入审查。新应用要保留这些价值，把支持范围延伸到一次任务的方向、交付核验、长期知识的适用性和人的维护判断。

用户明确要求：**新应用必须比 `agent-context-sync` 更完善、更好用。** 这是产品必须证明的目标。功能数量、文档数量、Skill 安装成功和一次演示成功，都不能单独证明达成。

## 2. 六项能力，分别交付什么

| 能力目标 | 维护者应当得到的结果 | 完成这项能力需要回答的问题 |
| --- | --- | --- |
| PC-G0 首次接入与项目建模 | 接入已有项目后，直接得到有来源的项目全貌、结构、关键流程、规范和未知项；从零项目先形成目标与设计模型 | 这个项目是什么、怎样组成和运行、我们已经知道多少，从哪里开始工作？ |
| PC-G1 保持任务方向 | 一眼能核对这次要改变什么、范围和完成条件；重要解释变化及时可见 | Agent 接到的任务还是我的原意吗？ |
| PC-G2 开发中及时使用相关知识与能力 | Agent 在任务开始及重要变化时主动找到规范、现有工具、踩坑经验和研发路径，核实后用于当前选择 | 项目已经能做什么、以前为什么这样做，这次哪些可以直接复用？ |
| PC-G3 核验交付 | 看见完成条件对应的产物、证据与未验证项，能够判断接受、补证或返工 | 到底做成了什么，凭什么相信？ |
| PC-G4 及时捕获并维护可靠知识 | 开发中发现的能力、验证过的经验和重要试验及时形成候选，接纳后供后续使用，并处理变化与冲突 | 哪些发现值得留下，何时记录，哪些已变或仍是推断？ |
| PC-G5 帮助人理解项目 | 按当前问题找到行为、关键取舍、改动影响和未知，并能回到来源 | 我能用这些资料作出下一次维护判断吗？ |

Agent 继续自主选择调查、工具、实现和验证方法。维护者主要负责目标、规范、架构取舍和风险接受。普通局部任务可以只用简短目标与结果核验；没有长期价值的发现不要求更新知识。

### 首次接入的两种起点

“新项目”首先按新接入工具、已有代码但没有本工具记忆的项目处理；同时覆盖从零创建的项目。前者是本次用户明确指出的能力缺口，后者的具体交互为补充设计提案。

| 起点 | 输入 | 首次应该得到什么 |
| --- | --- | --- |
| 已有代码，第一次接入 | 指定项目及可访问源码、配置、构建、测试、文档与决定；无需预先提供 Base 或会话历史 | 全项目调查结果、带来源和状态的初始认知模型、未覆盖与未知项、可供人理解和后续 Agent 使用的入口 |
| 从零创建或尚无实现 | 用户目标、使用场景、范围、约束及已有需求/设计材料 | 目标与设计模型，区分已确认意图、待决定取舍和拟议结构；代码出现后再补实现事实并核对设计与实现差异 |

已有项目的初始模型至少需要让人看清：

- **项目全貌：** 主要用途、输入输出、运行边界、技术组成和启动/构建/验证入口。
- **结构关系：** 主要模块的职责、依赖、接口、配置、数据与状态所有者，以及外部系统边界。
- **关键行为：** 从入口到结果的主要业务、数据或事件路径，以及与理解项目有关的错误、兼容和退出路径。
- **约束与决定：** 已有规范、确认来源和重要取舍；源码表现出的习惯与人类确认的规则分别表达。
- **可复用能力与经验：** 项目已有工具、脚本、入口、适用条件，以及有证据的踩坑经验和方案试验路径；它们需要能够按当前需求被找到。
- **可信范围：** 每项关键结论的来源、适用 revision 和状态，主要风险、冲突、未理解部分及后续调查入口。

这些内容构成可更新的知识与关系模型，并能生成易读入口。只有目录树或一份概述，尚不满足首次建模目标。详细调查材料与被接纳的长期知识分别保存；最初建模可以产生较大的知识增量，之后按变化更新。

### 全量扫描的完成边界

全量指**用户指定项目的整体调查范围**。所有第一方模块和影响行为的源码、配置、构建/部署及测试材料都应进入调查范围；从入口跨模块追踪主要关系，不能只分析一次局部修改涉及的文件。

项目范围先形成可核对的来源清单，记录哪些已调查、哪些只定位未理解、哪些被排除及原因。生成物、第三方依赖和二进制按其对项目行为的作用说明调查方式或排除理由；缺少访问权限、外部运行条件或时间不足的区域保持未完成。文件被枚举到不等于其语义已理解，源码静态解释也不等于运行已验证。

Agent 自主选择读取顺序、仓库原生工具和分批调查方式。大项目可以分段形成模型并继续补全，但局部完成时必须显示整体剩余范围；长期知识保留重要语义和来源，不要求把每个符号复制成记录。

## 3. 用起来应当是什么感觉

以下是由目标推导的体验要求，具体交互形态仍待审阅：

首次使用时，用户可以直接说“接入这个项目，完整调查并建立模型”。系统从可访问来源开始，展示调查进展和模型已覆盖部分，把需要人补充的业务意图或关键取舍集中呈现。用户仅提出局部任务时，仍可按局部范围工作，不强制先完成全项目建模。

1. **接着做时能直接开始。** 用户说“继续”或提出新任务，系统恢复相关目标、决定和下一动作；能查到的项目事实由 Agent 调查。
2. **工作中只突出当前重点。** 当前目标、重要偏差和需要人决定的事项容易找到。用户无需先学会记忆文件名、组件名或命令组合。
3. **收尾时可以作出判断。** 交付先回答做成了什么和证据是否足够；适合保留的知识以简短变化呈现。确认精确对应需要人判断的命题，既有授权持续有效。
4. **以后查项目时有可靠入口。** 用户按“为什么这样设计”“改这里影响什么”进入资料，逐步展开相关关系、未知和来源，并回到原问题。
5. **维护负担随实际变化增长。** 系统选择相关内容并整理记录，用户处理重要取舍；小任务不会固定生成一套资料或要求完整同步。

统一入口和连续体验属于产品目标。入口采用独立应用、宿主内界面还是其他形式，需要结合使用场景选择；这些界面名称和底层存储尚未冻结。

### 传播与接入目标

用户于 2026-09-07 明确要求做成方便传播的形式，并参考 Superpowers 与轻量插件的实际组织方式。产品应让其他使用者容易理解用途、安装、在自己的项目首次使用并继续维护；传播容易与执行可靠分别验收。

当前优先考察一个插件作为统一分发单元、内部共享少量 Skill 与必要运行能力的形态。具体清单、核心程序、项目数据位置和跨宿主适配尚未选择。首次安装的步骤、依赖与成本、自动能力是否启用、更新与停用后的知识保留、与已有插件共存，都需要进入使用负担比较。

这些体验细化为提案，见 [Superpowers、Context7 与轻量命令插件调研](../research/plugin-distribution-and-runtime-patterns.md)。方便安装不单独证明开发期间的相关知识已提供或正确使用。

### 开发中让相关记忆参与工作

用户报告：曾要求编写一个“mouse 的覆盖、转写工具”，但后续 Agent 不会被提醒项目还有这项隐藏能力，也较少主动读取踩坑经验或研发路径。此处保留为用户报告；本轮尚未核对工具入口、实现状态和当时执行记录，具体漏读原因未确定。

预期体验是：用户只描述要解决的问题，Agent 在决定重做之前，能发现相关现有能力，得到“能做什么、入口在哪、何时适用、已有证据与限制”的简短提示，按需打开来源，并判断直接复用、适配还是另做。旧能力已失效或不匹配时说明原因。用户无需记住它的名字并再次提醒。

读取与记录分别覆盖以下时机，细节为设计提案：

| 开发中发生的事情 | 应读取或检查什么 | 应形成什么记录 |
| --- | --- | --- |
| 新任务，或目标与方案发生实质变化 | 相关能力、规范、已确认取舍与适用经验 | 重要选择所依据的来源；有新意图时记录对应确认 |
| 准备新增能力、进入新模块或改变主要路径 | 可复用工具、现有入口、该区域的约束和历史尝试 | 新发现的隐藏能力或需要修正的模型关系 |
| 出现错误、重复尝试或判断受阻 | 相似症状、失败路径、验证条件和已知限制 | 先记录必要观察；原因未证实时保留待查，不立即写成通用经验 |
| 修复得到验证、方案试验结束、能力新增或被弃用 | 相关旧知识是否需要更新或失效 | 带条件与证据的经验、试验结果、能力变化或失效候选 |
| 用户纠正、任务交接或上下文收缩 | 最新决定、未解决问题和待整理候选 | 保留明确纠正与候选引用，避免只在最终收尾时记录 |

Hook 是可能的触发手段。产品需要先保证上述时机得到覆盖，再选择宿主事件、工具动作和 Agent 语义判断如何配合。重复事件可以合并，只提供当前有用的少量知识；普通任务不要求反复读完整历史或逐次确认。

## 4. 怎样才算超过 agent-context-sync

比较基线是用户当前使用的 `agent-context-sync`、启动 Skill 和实际项目约定。基线拥有的能力照常使用；不能通过拿掉现有规范或不给基线提供必要来源来制造优势。

| 门槛 | 拟定判据 | 失败意味着什么 |
| --- | --- | --- |
| 更完善 | 保留可靠接续、决策记录、推断标记和隐私边界；走通 PC-G0–PC-G5，覆盖首次无记忆接入、全项目建模、后续复用和人的实际判断 | 只能接续已经积累上下文的项目，或只新增文件、摘要和孤立功能，尚不能满足产品目标 |
| 更好用 | 核心任务完成质量不降低；重复解释、纠偏、找资料、复核和维护记录的人工负担出现可观察改善，用户认为值得持续使用 | 功能覆盖更广，但人要承担更多无法抵消的操作与维护成本，应缩减或调整方案 |
| 可以持续替代 | 新会话接续和项目变化后仍能正确使用知识；重要失败、未解决限制及完整使用成本有记录 | 一次成功只能证明局部可行性，仍需继续验证 |

这是验收设计提案。未来运行前要固定具体任务、必须保留的行为、观察方式及可接受的成本取舍。当前没有测量数据，不设定虚构的节省比例，也不宣称产品已经优于基线。

比较覆盖首次接入已有项目、从零项目建模、恢复中断工作、普通局部任务、结构性设计交付、来源变化后的后续任务和真实维护者判断。首次接入单独记录从无记忆到模型可用的人工与运行成本。完整比较方法见 [基线与候选资料](../research/capability-baseline-and-candidates.md#4-comparison-design)。

其中还要检验：未点名的隐藏能力是否在重复实现前被发现并核实；开发中捕获的经验是否在后续相关时机被实际使用。已保存、已提供给 Agent、已查阅、已用于判断分别记录；Hook 触发次数和记忆条数不单独代表成功。

## 5. 从目标反推职责

| 为什么需要 | 应有的逻辑职责 | 输入 → 可见输出 | 后续实现选择的依据 |
| --- | --- | --- | --- |
| PC-G0 | 项目接入、全局调查与模型归纳 | 项目来源或目标资料 → 覆盖说明、初始模型、来源关系和待核实项 | 观察首次接入是否遗漏主要模块、凭空补齐原因，或把目录摘要当成模型 |
| 用户需要持续掌握当前工作 | 产品交互与任务状态 | 自然语言请求、已有上下文 → 当前目标、进展、待决定事项、交付入口 | 观察用户在哪里需要来回找信息或重复操作 |
| PC-G1、PC-G2 | 任务边界与开发中的相关知识选择 | 原请求、当前动作、问题线索与项目知识 → 可核对目标、相关能力/经验及其适用依据 | 观察误解方向、隐藏能力漏用、重复踩坑和无关资料干扰 |
| PC-G3 | 结果核验与证据关联 | 完成条件、产物和实际证据 → 满足、未满足或尚未验证的判定 | 观察完成声明与实际结果脱节的失败 |
| PC-G4 | 开发中捕获、知识准入和生命周期 | 新能力、失败/试验结果、来源变化、人类决定 → 及时保存的候选与可复用知识 | 观察中途发现丢失、错误经验晋升、知识误用和维护成本 |
| PC-G5 | 围绕问题组织人类资料 | 读者问题、同一批长期知识 → 可理解的说明、关系和证据入口 | 观察人是否真的能定位影响、未知和待决定事项 |
| 接续、跨工具使用与可追溯 | Agent/项目适配与记录 | 既有 Agent、项目资料与授权 → 可接续任务和可追溯引用 | 只为已观察到的集成、持久化和确定性校验缺口添加机制 |

这些职责可以由同一组件承担。Skill 可以承载可复用任务方法，已有工具可以承担存储或集成，Agent 承担语义理解。组件选择要同时说明覆盖了哪个目标、增加什么负担、为什么已有能力不足。
