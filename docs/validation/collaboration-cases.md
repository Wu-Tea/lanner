# 协作能力验收设计

状态：2026-09-22 proposed；本文定义输入和预期性质，没有执行产品测试。静态文档核验不计为本表通过。旧单任务和知识能力继续使用[Golden Cases](golden-cases.md)回归。

## 1. 首个验证切片

先用[合成例子](../guides/cognition-flow.md)校准理解，再固定一个用户授权的真实项目。至少包含一条工作线、两个有依赖的任务、三个可区分 session、一份附加材料、一次明确决定变化，以及一个基于旧前提的未完成任务。

运行前固定：原请求、项目 revision、来源清单与权限、初始模型/决定、参与者与授权、Task 完成条件、输入出现顺序、模型/宿主、核验者与预算。候选输出出现后不能静默改验收条件。

真正的未知材料用于后续任务，不把预期答案混入给执行者的输入。模型模拟参与者标为 synthetic；真实多人和并发验证需要真实运行记录。

## 3. 核验分工与记录

语义条件由核验者对照原始输入与实际结果判断，关键决定来源需打开检查。确定性引用、去重、读入版本、权限与持久化在有实现后用机器测试；单份设计文档不能证明这些保障。

记录模型自查、独立评审、人工接受和真实运行各自的范围。引用不可访问时，相关条件保持尚未验证。没有合格参考答案时先记录分歧与理由，不能用另一段摘要当作真值。

## 4. 价值与成本比较

基线是用户实际使用的 agent-context-sync 加既有项目规则与协作工具；给双方相同来源、任务序列、规范、权限和资源，说明模型或环境差异。任务顺序与评审尽可能减少答案泄漏和学习效应。

观察：目标偏差、依赖/决定遗漏、错误完成声明、冲突返工、人工补背景/纠偏/协调次数、记录维护时间、额外模型成本及维护者使用意愿。等待时间、在制工作和交付周期只有在开始/结束口径一致且有数据时报告，不拿 Agent 数或记录数代替收益。

普通任务不能因新框架明显增加无补偿的负担；跨任务获益也不能抵消隐私泄露或未经授权的承诺。阈值和成本取舍在真实运行前与具体场景绑定，不预设虚构比例。
