# CASE-20260908-001：找到旧成果之后，为什么仍然反复走偏

来源：[实现原生鼠标屏蔽算法](codex://threads/01a07c11-d7e0-78e1-be00-e6639a0b9aec)，项目 `yolo-study-001`。分析日期：2026-09-08。案例判断由 Agent 提出；下文验收建议为 proposed。

## 这个案例说明什么

用户希望利用已有鼠标研究和当前 gamepad 控制逻辑，做出能屏蔽、转写物理鼠标信号的 mouse controller。任务后来补充了默认运行、AutoFire、频率和手动输入裁决要求。

该任务第一轮就找到了旧工作目录，也读取了鼠标适配与最终输出决定。因此，本案最有价值的证据落在“找到之后怎样理解、复用、执行和留下纠正”。初步判断（inferred）：六项能力目标基本能容纳这些问题，但资料存在、Skill 被读取、测试通过，都不足以单独证明能力达成。

这里分析 Agent 的工作行为，不评价鼠标程序的最终实机质量。已通读 8 轮用户要求和最终回复，定向核对关键命令、补丁及交接读取；207 份命令输出中有 57 份被接口截断。必要摘录与原任务定位保存在 [evidence.json](evidence.json)，未保存完整对话、内部推理或私人视频，未重跑源项目。

## 主要发现

### F1：已读到原则，仍需要用户把它翻译成当前实现的判断方式

**观察：** T8 在修改前读到了 8 月 7 日的已接受决定：原始手动输入不是必须保留的输出项，可以削弱或忽略，最终输出由控制器统一求解。随后补丁先缩放 manual 权重，继续进入原有合作/阻尼分支。用户再次指出“先判断是否削弱用户输入，覆盖转写就是为了这个目的”后，才加入 mouse 直接选择最终轴的路径，以及相同目标指令在零、同向、反向手动输入下得到相同结果的断言。证据 E10–E16。

**判断（inferred）：** 知识已提供、已读取，却没有充分转成当前场景下的适用性判断与验收条件。复用共享控制器时，需要核对设备语义、手动输入的作用和输出责任，不能仅凭“与 gamepad 一样”沿用全部历史行为。责任主要在方案适配与结果核验。

这里不能把内部阻尼分支写成“发送了两路物理鼠标位移”：记录表明改动前后都主张唯一最终输出。T8 的具体直接裁决规则在用户纠正后才明确；旧的最终输出原则与其相关，但不能把后来形成的每条断言倒写成最初已有要求。

### F2：开发发现写进了说明，却没有通过交接入口形成可靠接续

**观察：** T1、T4、T5、T6、T7、T8 六次最终回复建议同步上下文。T1、T3、T5、T7 两次及 T8，共六次 handoff 读取仍显示 9 月 1 日的 Fusion 显示恢复任务。可见 fileChange 没有 `.agent-context/` 变更，含该路径的命令中也未发现显式写入。实现说明确实被更新过，不能说完全没有记录。证据见 evidence.json 的 `context_audit`。

**判断（inferred）：** 本任务的重要新要求与纠正，没有经该交接入口形成稳定接续；继续增加“请记住”的文本很难解决这段断开。责任在开发时捕获、准入状态和后续上下文选择之间的连接。

这不是对当时写入权限违规的判定，也不能排除其他任务或间接工具写入。未来产品应在已授权范围内完成捕获和记录；需要确认的内容保留候选及待处理状态。不同任务的当前进度要各有范围，不能为更新 mouse 而覆盖仍有价值的 Fusion 状态。

### F3：旧成果的可复用部分与未完成部分没有稳定地区分

**观察：** T1 找到旧方案并集成到当前 controller，但默认驱动入口当时没有可用设备接口。T2 正确指出旧 demo 与测试没有证明完整连续 X/Y 接管，随后 T3 转向独立工具与 Interception 驱动路线。T4 用户强调已有研究足以作为继续编码的基础，Agent 才回到 Win32 路线，补接入与联调。证据 E01–E09、E21。

**判断（inferred）：** “机制可以复用”“系统可直接运行”“目标环境已经验收”需要分别判断。部分机制有价值，不代表整个旧应用可交付；缺少整体验收，也不自动否定已有研究。责任在能力模型与方案选择，尤其是从缺口推导新增依赖之前。

T3 用户明确要求一条可用的链路工具，所以不能把独立工具工作一概判为未授权。新驱动是否完全没有必要，也不能仅凭后来的桌面运行或“能够触发”判定；缺的是路线取舍与当前目标之间足够清楚的依据。

### F4：局部验证和用户期待的可用结果，需要在同一处对照

**观察：** T1 已有 17/17 原生回归、20/20 启动脚本测试和驱动构建结果，但默认入口仍会报告设备不可用。T4 又获得桌面透传与正式程序运行证据；目标游戏内排除原始输入的边界仍单列未验收。T8 的新策略是在已有调速回归之后，经用户纠正再补入。证据 E04、E15–E16、E21。

**判断（inferred）：** 结果核验应对应当前完成条件，分别说明算法、入口、输入输出行为和目标环境覆盖了什么。具体分层随任务变化，不要求每个任务固定生成一套测试。

该 Agent 多次主动说明实机与游戏内限制，不能把本案概括为“谎称所有功能已验收”。真正值得补强的是：用户能否立即判断自己的当前目标还差哪一段，以及局部成功是否足以支撑所选择的路线。

## 有些后续消息属于新增要求或待核实判断

- T5 的未校准默认运行与具体参数是新指令；T1 读到的旧决定确实描述了校准路线，不能要求 Agent 预先知道新参数。证据 E03、E19。
- T6 明确保留原始操作并接通 AutoFire。核对发现当时 C++ hook 已放行按钮，实际缺口是 AutoFire 未接线及旧调试入口仍走 Python；不能照搬“仍在拦截左右键”的前提。证据 E17 及 T6 最终回复。
- T7 用户担心只有 250 Hz，Agent 实测接近 1000 Hz，并区分目标频率、控制循环与接收端频率。这是值得保留的正确处理。独立调度要求仍可以落实，不能把未证实的降频写成已修复缺陷。证据 E18 及 T7 最终回复。
- T8 用户报告已经能够触发，支持该次体验反馈；它不独立证明全部输入屏蔽、游戏接收与故障恢复要求。证据 E20。

## 建议细化已有验收，不新增顶层能力

以下为 proposed，可作为已有 Golden Case 的变体，尚未写入正式验收或执行试验：

| 变体 | 应能区分的行为 | 现有归属 |
| --- | --- | --- |
| 已读原则仍用错 | 原则明确提供后，能指出其对当前选择的约束；检查可观察行为，不能以引用或读取次数计为遵守 | GC-004、GC-012、GC-017 |
| 部分成果复用 | 面对不完整 demo，区分可用机制、所需适配和未验证范围；既不过度相信，也不无依据地全部重做 | GC-017 |
| 路线增加新前提 | 准备引入驱动、重启或独立工具等实质代价时，说明它解决哪项缺口、已有路线为何不够及对当前交付的影响 | GC-001、GC-003、GC-011 |
| 纠正之后能接续 | 已授权捕获/写入有实际结果；需确认的候选可恢复；后续任务取回新要求并正确应用，旧任务资料不被覆盖 | GC-007、GC-008、GC-013、GC-018 |
| 用户判断也要核实 | 同时提供明确新要求与未经证实的故障猜测，能落实要求并纠正错误前提，不编造故障或扩大验收 | GC-005、GC-012 |
| 使用负担可见 | 比较重复解释、纠偏、无关读取、确认与记录维护的成本，确认能力增强是否值得持续使用 | GC-006、GC-014 |

从职责看，需要继续检验的已有组件是任务方向维护、知识选择与适用性判断、结果核验，以及开发中捕获到后续读取的连接。Skill 可以指导判断，工具可以完成已授权记录、引用和状态检查；是否需要哪些 Hook、宿主适配或运行核心，仍待实际试验，不能由本案直接冻结。

## 后续怎样使用这个案例

优先用本案细化“已读原则仍用错”和“纠正后能接续”两个验收变体，再比较现有方案能否覆盖。每次回放只提供当时已经可用的请求、来源和确认；后来的用户纠正用作后续阶段材料，不能提前泄漏答案或把新要求计为此前的失败。

目前没有取得完整可重放的源码与运行快照。任务所在 dev 与旧工作目录有未提交状态，不能套用本仓库早期 yolo Golden Case 的固定 revision。本轮只有历史观察，既没有对照试验，也没有新会话使用收益或成本测量。

本案的鼠标技术选择、参数和项目规范只适用于其来源范围。产品仍处于 R1；能力目标与案例前 [历史基线](../../../.agent-context/baselines/BASELINE-2026-09-07-001.md) 保持原边界，本轮仅给目标说明补充案例来源。下一步是审阅这些验收细化建议。
