# 从检查三台设备开始，读懂 recommendLines

假设学校有一些水泵，需要有人定期去看看：有没有漏水，运行时有没有异常声音。检查完，还要在手机上填写结果。这样按要求走到设备旁边、查看情况并记录下来的工作，在这个项目里叫“巡检”。下面的学校和设备都是讲解用的虚构例子。

今天，小林要检查设备 01、02、05。三台都要检查，但顺序还没有定。他可以先去 01，再去 02，最后去 05；也可以先去 01，再去 05，最后去 02。走的地方相同，先后次序不同，花的时间可能不同。

`recommendLines` 要做的事，就是接收“今天要检查这几台设备”，算出几个检查顺序，交给页面展示。这里的一条“路线”，先理解成一个排好顺序的设备列表即可。

## 1. 程序已经有什么，还缺什么

程序不需要重新发现学校有哪些设备。设备和检查要求之前已经录入系统了，今天只是从中选几台。

先看两份简化的数据。下面的字段和值用于解释关联关系，不是可以直接导入原数据库的建表文件。

**一份记录设备本身的信息：**

| 设备编号 | 名称 | 在哪里 |
| --- | --- | --- |
| 101 | 设备 01 | A 区，1 层，101 室 |
| 102 | 设备 02 | A 区，1 层，102 室 |
| 105 | 设备 05 | B 区，1 层，101 室 |

项目里把这类设备资料叫“资产信息”。这里的“资产”不涉及财务计算，先理解为登记在系统里的设备。

**另一份记录哪些设备被纳入检查：**

| 检查对象编号 `objectId` | 对应的设备编号 `capitalId` |
| --- | --- |
| 1 | 101 |
| 2 | 102 |
| 5 | 105 |

被纳入检查的设备，在代码里叫“巡检对象”，用 `InspectObject` 表示。上面第一行的意思是：“编号为 1 的检查对象，检查的是编号为 101 的设备。”两个编号属于不同的记录，所以不能混用。

如果你写过关联查询，这个关系就很熟悉了：先查到一行，再拿它的 `capitalId` 找到对应的设备资料。原项目有些资料要调用另一个服务的接口来查，并不一定在同一个数据库里做 JOIN，但最后同样是把相关字段放到一起。

设备资料还提供坐标。坐标是用两个数字表示位置的方法：代码用 `smx` 存经度、`smy` 存纬度。两个位置之间有多远，由现成的距离计算函数处理。这一节只需要知道它接收两台设备的位置，返回一个距离数值，不需要先学会地理公式。

此外，系统保存着以前的检查记录。作者希望从中看出：大家以前是否经常检查完设备 01，就接着去设备 02。这个信息可以给今天的安排提供参考。

所以，这个方法要用到的资料是：**今天选中的检查对象、它们的位置、它们所在的楼栋和房间，以及以前的检查顺序。**

## 2. 页面怎样告诉程序“今天查这三台”

页面向 `/api/inspect/line/recommend/list` 发送下面的请求。你可以把这个接口理解成一次普通的后端方法调用，只是参数通过 HTTP 传过来：

```json
{
  "objectIds": [1, 2, 5],
  "smx": "10.0005",
  "smy": "20.0005",
  "startObjectId": 1
}
```

`objectIds` 表示这次要检查编号为 1、2、5 的对象。注意传的是上一节第二张表里的检查对象编号，不是 101、102、105 这些设备编号。

`startObjectId: 1` 表示从设备 01 开始。如果没有指定起点，程序就用 `smx`、`smy` 表示的当前位置，找出离小林最近的一个检查对象，从那里开始。这些示例坐标是虚构的。

Controller 的工作很少：从请求里取出这四项，调用 `inspectLineService.recommendLines(...)`，再把结果返回。接下来的查询和计算都在 Service 及它调用的工具方法里。

## 3. 先查数据，把每台设备的信息放到一起

原代码的注释先写“查询对应 id 的路线列表”，实际查到的是本次要检查的对象列表。用你熟悉的 SQL 表达，就是下面的意思；这只是查询思路，不是原项目可直接执行的 SQL：

```sql
SELECT * FROM 检查对象 WHERE objectId IN (1, 2, 5);
```

这时已经知道对象编号及其 `capitalId`，但计算所需的位置还没有全部补齐。代码接着做两件事：

- 调用 `translateUtils`，按设备编号查出设备资料，放进对象的 `capitalModel` 字段。“translate”在这里是补资料，不是翻译语言。
- 调用资产扩展查询接口，补上楼栋、楼层和房间。查询时还会带上 `kindId`，用来说明设备属于哪一种类别。

完成后，可以把一个对象想成下面这样。这里只展示本次计算用得到的部分字段：

```json
{
  "objectId": 1,
  "capitalId": 101,
  "capitalModel": { "smx": "10.000960", "smy": "20.001100" },
  "buildingName": "A 区",
  "floorName": "1 层",
  "roomName": "101 室"
}
```

现在有了 `objectList`，里面装着三台设备的完整计算资料。后续主要是在内存中读这个列表、写数组和做计算。

## 4. 两台设备之间，用什么判断是否适合接着检查

先站在小林的角度想。设备 01 和 02 离得近，又在同一栋楼的同一层，通常值得放在一起考虑；如果过去也经常先检查 01 再检查 02，这又提供了一条参考。

程序不会理解“顺路”这句话，需要把这些条件变成数字。代码的做法是：先根据距离得到一个数值，再因为同楼、同层或历史顺序而减掉一些数值。**减完的数越小，搜索时越倾向于考虑这两个设备之间的连接。** 这种用来影响选择的数字，代码称为“权重”。

下面先只看从设备 01 去设备 02。为了便于手算，暂时假设它们之间的距离是 100 米，历史上“检查 01 后接着检查 02”出现过 30 次。这两个数是教学假设，不是前面坐标算出的结果，也不是 Demo 默认数据。

距离部分：代码把距离除以 100，因此得到 `100 / 100 = 1`。

楼栋和房间部分：按楼栋、楼层、房间依次比较。楼栋相同减 5，接着楼层也相同再减 5；房间不同，到这里停止，所以一共减 10。不能跳过楼栋直接比较房间号：A 区的 101 室和 B 区的 101 室并不是同一间房。

历史部分：代码把相邻次数除以 10，这里是 `30 / 10 = 3`，因此再减 3。于是得到：

```text
从设备 01 去设备 02 的分数 = 1 − 10 − 3 = −12
```

负数在这里允许出现，因为这是程序比较选择时用的分数。距离仍是假设的 100 米，不会因为减成了 −12 就变成负的路程。

## 5. 对每一对设备都算一遍，再装进二维数组

不能只算 01 到 02。程序还要知道 01 到 05、02 到 05，以及反方向的数值，所以需要遍历整个列表。

假设 `objectList` 的顺序是设备 01、02、05。我们继续用手算距离：01 与 02 相距 100 米，01 与 05 相距 300 米，02 与 05 相距 250 米。除以 100 后，可以排成这张表：

| 从哪台出发 ↓ / 去哪台 → | 设备 01 | 设备 02 | 设备 05 |
| --- | ---: | ---: | ---: |
| 设备 01 | 0 | 1 | 3 |
| 设备 02 | 1 | 0 | 2.5 |
| 设备 05 | 3 | 2.5 | 0 |

例如，第 1 行第 3 列的 `3`，就是从设备 01 到设备 05 的距离数值。去自己那里不需要走路，所以对角线是 0。

代码把这种按行列排好的数值叫“矩阵”。它在这里就是一个二维数组，可以用两层 `for` 循环填写：

```java
// 讲解用的伪代码：方法名已简化，不能直接复制运行。
for (int i = 0; i < objectList.size(); i++) {
    for (int j = 0; j < objectList.size(); j++) {
        distance[i][j] = 计算距离(objectList.get(i), objectList.get(j)) / 100;
    }
}
```

同样的方法还能整理出另外两张表：一张存同楼、同层、同房间应减的数值，另一张存历史顺序应减的数值。三张表必须用同一个对象列表的顺序。否则，一张表里的第 1 行代表设备 01，另一张却代表设备 05，相减时就把不同设备的数据混在一起了。

原注释接下来写“合并距离矩阵和楼栋权重矩阵”，再“合并所有权重矩阵”，意思就是逐个格子做减法：

```java
finalWeight[i][j] = distance[i][j] - buildingWeight[i][j] - historyWeight[i][j];
```

沿用前面的例子：01 和 02 同楼同层，各方向都减 10；历史只假设 01→02 有 30 次，其余方向没有。最后得到：

| 从哪台出发 ↓ / 去哪台 → | 设备 01 | 设备 02 | 设备 05 |
| --- | ---: | ---: | ---: |
| 设备 01 | 0 | −12 | 3 |
| 设备 02 | −9 | 0 | 2.5 |
| 设备 05 | 3 | 2.5 | 0 |

为什么 01→02 是 −12，02→01 却是 −9？因为同楼同层的条件双方都满足，但这里的历史只说明以前常从 01 去 02，没有说反方向也出现过 30 次。

## 6. 有了分数，怎样生成一个检查顺序

现在已知从设备 01 开始，剩下两台还没决定顺序。原代码会分别尝试“第二台先去 02”和“第二台先去 05”。每次算出的顺序叫一条“候选路线”，也就是先留着比较的一种方案。

为了让指定的第二台优先被考虑，代码临时把起点与它之间的两个方向都设成 `-1000`。这个数比刚才表中的数值小很多。每次尝试使用矩阵的副本，所以不会把上一次改成的 `-1000` 留到下一次。

后续使用一个“待处理列表”，每个待处理项带着当前算到它的累计分数。每次取分数最小的一项，若这台设备还没被加入结果，就把它加入，再计算从它到其他未处理设备的分数。已加入结果的设备不再重复加入。代码用 `PriorityQueue` 来管理这个列表；它可以按设定的比较规则取出当前分数最小的一项。

“累计分数”就是在一次尝试中把经过连接的分数加起来。以优先去 02 为例，实际可以这样跟着算：

| 正在处理哪台 | 这一步算什么 | 已排好的顺序 |
| --- | --- | --- |
| 01 | 去 02 的分数临时设为 −1000，去 05 是 3；待处理列表先取较小的 −1000 | 01 |
| 02 | 从这次尝试继续去 05：−1000 + 2.5 = −997.5，比直接去 05 的 3 小，更新待处理项 | 01 → 02 |
| 05 | 05 第一次被取出，加入结果；三台都处理过了 | 01 → 02 → 05 |

同一设备可能有早先放入列表的旧条目。后来再取到它时，因为已经处理过，就跳过。代码还会比较新旧累计分数，只在新算出的更小时加入新的待处理项。

这里需要注意：这段程序会从不同的待处理项继续计算，不是始终站在最后加入结果的设备上选最近的一台。输出顺序是各台设备首次被取出的顺序，不能把它简单改写成“每一步都选离当前位置最近的设备”。

对于本节只有三台设备的例子，两次尝试分别得到：

```text
先尝试去 02：设备 01 → 设备 02 → 设备 05
先尝试去 05：设备 01 → 设备 05 → 设备 02
```

原方法注释提到了不同算法，但当前实际是反复调用同一个 `AStarPathfinding` 类，改变优先的第二台。读懂这段业务流程不要求先掌握 A*；也不能仅凭类名就认定它算出的是所有可能顺序中最短的一个。

## 7. 最后比较路程，整理成页面需要的结果

搜索分数已经完成了它的工作：帮助生成检查顺序。展示给人的路程，还要沿每个顺序重新把相邻设备的距离加起来。

继续用刚才的手算距离：

| 访问顺序 | 路程怎样相加 | 总路程 |
| --- | --- | ---: |
| 01 → 02 → 05 | 01 到 02 的 100 米，加上 02 到 05 的 250 米 | 350 米 |
| 01 → 05 → 02 | 01 到 05 的 300 米，加上 05 到 02 的 250 米 | 550 米 |

这里没有再从最后一台走回第一台，也没有加上小林当前位置到第一台的路程。代码汇总的是返回列表中相邻设备之间的距离。

代码按总路程从小到大排序，再选出最多三条。本例只有两次尝试，所以最多两条；设备更多时，当前规则取第一条、第二条，以及第 10 条（超过 10 个候选时）或最后一条。它没有把重复的检查顺序去掉。

返回数据中的 `pathNodes` 就是排好顺序的对象列表，`totalDistance` 是总路程，`eta` 是预计需要多少秒，`name` 和 `type` 用来显示名称与标签。`pathNodes` 里放的是对象数据，不只是编号。

预计时间的算法是假设每小时走 5 公里，走路时间再乘 1.2，给绕路留出一些时间，最后每台设备再加 25 秒的检查时间。这些是代码里写定的估计，不能据此认定真实检查只需要 25 秒。

**当前代码还有一处会直接影响读者理解结果的处理。** 第二条算完后，总路程会被改成第一条的约 92%–98%，但检查顺序和预计时间没有重算。假设本例随机取到 95%，第二条原本的 550 米就会显示成 `350 × 95% = 332.5` 米。原注释对此直接写着“造假数据”。因此不能拿当前显示值判断第二条确实更短。

此外，原距离函数本身也存在单位和参数顺序问题。上面的手算例子用于理解数据处理，不代表原服务能正确算出这些米数。另外，原历史查询按整次任务的创建时间排列记录；同一任务的这个时间相同，不能靠它分清三台设备到底谁先检查。因此历史顺序也需要继续核实。具体源码和数值核对放在文末。

## 8. 到 Demo 里把这条过程看一遍

[打开本地演示](../../../demos/recommend-lines/index.html)，或按 [运行说明](../../../demos/recommend-lines/README.md) 解压后打开。Demo 是能实际运行的小程序，设备、位置和历史数据都是专门编造的，不需要连接学校或原项目的数据库。

先只保留设备 01、02、05，选择设备 01 为起点，再点击“生成候选路线”。查看两条结果的顺序；下面打开“合成数据”，就能看到参与计算的设备资料。Demo 使用自己的坐标和历史数值，结果不会等于上面的手算假设。

然后进入“计算过程”，用下拉框依次选择“距离矩阵”“空间奖励”“历史边权”“合并权重”。现在你可以把这些名字分别读成：距离换算的数值、同楼同层要减的数值、历史顺序要减的数值，以及三者相减后的结果。对照同一行同一列，就能检查它怎样算出来。

最后取消“考虑楼栋、楼层与房间”或“考虑合成历史偏好”，重新计算，看哪些格子变了。路线顺序不一定每次都变化，但你能看到这项输入有没有进入计算。

“原逻辑移植”表示用 JavaScript 重写了原 Java 的处理步骤，保留了上述距离问题和随机改写；“距离校正对照”修正这些距离计算和显示问题，方便比较。两个模式都没有学校道路、围墙、楼梯等资料，不能直接当成带人实地行走的导航。

| 历史窗口在 `PARTITION BY task_id` 内按同一任务的 `task.create_time` 排序 [S11](evidence/source-catalog.md#s11) | 同一任务内排序键相同 → 无法由该键确定实际对象巡检先后 → 历史权重不等于可信访问次序 | SQL 事实；未运行数据库。需选择真实事件时间/顺序来源，补重访、并列时间和采样边界 |
| 缺坐标在矩阵中被大值惩罚，但路径汇总把该段距离当 0；找最近点又直接解引用模型 [S12–15](evidence/source-catalog.md#s12) | 不同阶段对“未知位置”含义不同 → 搜索代价、排序与输出会分歧，部分输入可能异常 | 静态路径事实；未调用真实 API。应在位置数据边界明确未知值政策 |
| 某些 Future 失败抛运行异常，后半段捕获另一些异步失败后返回空列表 [S06](evidence/source-catalog.md#s06) | 依赖失败可能与没有候选得到相同成功空列表封装 | 代码可见；实际异常响应、客户端表现和弹性政策未验证 |

## 后续维护可直接使用的检查顺序

1. 先确认用户希望优化的是可通行距离、总耗时、对象访问顺序，还是候选展示；三者当前没有统一的已确认目标函数。
2. 核对资产数据的坐标顺序、单位、缺失比例，以及楼栋/楼层/房间层级语义。
3. 取一条真实历史任务，确认对象检查先后来自哪个字段；不要从任务创建时间反推对象访问顺序。
4. 如获准修改，以结果必须覆盖的对象、起点语义、节点/距离/ETA 一致性和异常语义为验收，再选择算法。
5. 同时验证 0/1/2/多对象、无效起点、缺坐标、资产服务失败、重复候选及相同请求的稳定性。真实运行和性能需要另行提供可用环境。
