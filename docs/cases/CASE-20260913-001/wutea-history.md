# wutea 改过哪些功能，这些改动解决什么事

假设小林要按学校安排检查几台设备，在手机上领取今天的工作，查看设备名单，逐项填写结果，最后提交并生成记录。这些工作就是下面代码改动的业务背景。不了解“巡检”时，可以先读 [一次设备检查](business-map.md)。

这个项目使用 Git 保存代码修改历史。每次保存的修改叫一次“提交”，通常带着作者名、修改的文件，以及作者填写的一句说明。`wutea` 是本次要检索的作者名。我们查看这些记录，是为了理解相关功能怎样改到今天这样。

## 先看改动影响了什么工作

| 使用者做什么 | wutea 的相关改动涉及什么 |
| --- | --- |
| 查看今天的任务，确定由谁检查 | 任务查询、执行状态、负责人，以及把未开始的工作交给其他人的“委托”操作 |
| 查看要检查哪些设备、先去哪一台 | 路线、检查计划、设备位置查询，以及推荐访问顺序 |
| 在手机上完成检查并提交 | 手机里暂存的数据怎样上传，检查答案、扫码记录、照片等怎样保存 |
| 检查之后查看记录 | 查询结果、生成报告、导出 Excel，以及查看设备过去某次检查时的情况 |
| 跟进发现的漏水等问题 | 从另一个处理问题的系统接收“已处理”等状态，更新本地记录 |

因此，只看 `recommendLines` 还不能覆盖这个作者的主要工作。他也修改了任务安排、提交保存和结果查询。

## 两段值得连起来看的修改

路线推荐先出现接口和计算代码，随后补设备位置、楼栋等资料，调整如何指定起点、怎样计算距离，以及最后展示哪几条结果。阅读当前代码时，必须把“查出设备位置”和“拿位置算顺序”连起来看，不能只看一个名字叫寻路的类。[推荐方法入门](route-recommendation.md) 已按这个顺序展开。

提交保存则经历了不同写法。有些修改把多条记录一起保存，有些又改回一条条保存，后来把部分数据交给后台通过消息队列保存。消息队列的用途是先接收待处理数据，再让另一段代码取出并保存；详细背景见 [提交说明](submission-reassessment.md)。

这里要区分“检查答案”和“扫码记录”。有一次提交标题提到了检查明细，但实际改回逐条保存的是扫码记录。修改说明只是作者当时写的一句话，判断改了什么还要看代码差异。

## 读历史时怎样避免误解

下面出现的 `7f4d450a` 等短字符串，是一条提交的编号，方便精确找到那次修改。`HEAD` 指本次查看的当前代码版本；“当前 HEAD 可达”表示这条提交属于当前版本追溯得到的历史，不表示它改过的每一行今天还原样保留。

本地查到作者名严格为 `wutea` 的提交共 88 条，其中 81 条属于当前版本历史。这不是他的全部职业贡献，也不表示这些模块只由他一人编写。本次没有去远端服务器获取更多历史。

理解了这些含义后，可以按下面的主题和编号找具体文件。表里明确写“只看过标题或路径”的内容，是查找线索；写“已核对代码差异”的内容，才表示本轮实际读过相关改动。

## 提交存储怎样演变

这里有一个不能省略的粒度区别：**检查明细 `InspectRecordDetail` 与扫码记录 `InspectScanCodeRecord` 是不同对象。**

- `ffb723cb` 的标题指向检查明细批量新增；本次只定位标题/路径，不能断言其全部实现与后续效果。
- `c990226e` 的标题提到 record detail，但它与 `6a2b50f8` 的反向变更涉及扫码保存。已打开 `6a2b50f8` diff：恢复 `inspectScanCodeRecordService.saveOrUpdate`，停止收集后 `saveOrUpdateBatch(...,20)`。因此这里应登记为“扫码记录从批量改回逐条”。
- `403675b6` 已核对关键 diff：检查明细、附件、扫码和结束任务的坐标改用消息发送，增加 Redis 缓存，并新增消费者/队列相关文件；`203c1961` 再将正常登记改为 MQ。
- 当前 V2 仍包含同步写和异步写，接口成功没有等待所有消费者完成。要研究性能或一致性，应从 [V2 生产端 S23–24](evidence/source-catalog.md#s23) 与 [消费端 S25–26](evidence/source-catalog.md#s25) 同时进入。

**第二轮补证**：用户提供的 [提交优化方案](submission-reassessment.md) 解释了附件独立上传后，仍有同步写库耗时、前端超时和部分成功无法确认的问题，因此采用已有 RabbitMQ 机制做异步写入；文档补记 2025-05-28 15:00 完成，与 05-27/28 相关提交日期相邻。这能保留文档所述业务动机，但不能直接证明版本上线或收益达标。

**仍缺失的历史**：为什么扫码批量方案回退、当时是哪种性能/驱动/数据语义问题、MQ 前后吞吐与失败率、是否发生过重放或数据不完整。方案提出幂等/重试/补发设计，实际效果仍需日志和试验结果；不能晋升为“批量保存不可用”或“MQ 已解决全部性能与一致性问题”。

## 巡检时间如何影响对象快照

最新 `8af0fc2d` 的标题是“巡检时间由数据库创建”，实际 diff 仅删除发送检查明细消息前的 `setInspectTime(new Date())`。当前 `InspectRecordDetail.inspectTime` 字段存在；快照查询会调用 `getInspectTime().toInstant()`。[S37](evidence/source-catalog.md#s37)、[S36](evidence/source-catalog.md#s36)

本次在仓库 Liquibase 文件中检索 `inspect_time` / `INSPECT_TIME`，只命中其他字段如 `INSPECT_TIME_CONSUMING`，未定位该列的默认值迁移；mapper 接口继承 BaseMapper，未发现对应独立 XML。因此数据库生成机制仍是未知，不能凭提交标题补成已实现事实。已有部署可能通过仓库外 DDL 或其他机制设置，需查实际表定义。

后续维护关系为：**发送端不赋值 → MQ 消费保存 → 数据库是否产生时间 → 快照读取时间**。该链比孤立记下“加了一个时间字段”更能指导改动，但尚未复现生产空值异常，也不能宣布已找到线上故障。
