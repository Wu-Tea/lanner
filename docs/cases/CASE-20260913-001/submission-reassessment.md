# 检查完三台设备后，为什么点“提交”还要等很久

假设小林完成了学校三台设备的检查，在手机里填好了答案，还拍了漏水照片。现在要把这些内容交给服务器，其他人才能查到。这一步就是“提交巡检结果”。巡检是按安排查看设备并记录情况；下面的学校例子是虚构的。

你熟悉的 CRUD 保存接口，可能是收到一条 JSON，然后执行一次 INSERT。这里的提交看起来也只有一个按钮，但按钮背后可能要保存很多检查答案，还要上传照片。用户提供的优化方案说明，原来这一步容易等待很久，甚至让手机提示失败。

## 先拆开看：这个按钮到底提交了什么

假设每台设备需要回答两个问题，三台设备就有六条答案。此外还有这次任务的完成状态、一张照片，以及可能的扫码、位置记录。

| 内容 | 一条例子 | 为什么要保存 |
| --- | --- | --- |
| 本次任务 | 今天上午的检查已结束，执行人是小林 | 区分这一次检查与昨天、明天的检查 |
| 每项检查的答案 | 设备 01 的“是否漏水”填写“是” | 以后能查到哪台设备、哪次检查、哪项内容出了问题 |
| 问题记录 | 设备 01 漏水，需要处理 | 后续记录处理情况；项目把这种异常叫“缺陷” |
| 照片及其关联 | 这张照片属于设备 01 的本次检查 | 从检查结果找到对应照片 |
| 执行过程 | 扫过哪个设备的码，在哪里检查 | 保留执行过程的信息 |

这些数据通过任务编号、对象编号等字段关联。检查对象就是被纳入检查的设备记录，详见 [业务入门](business-map.md)。只存一张照片却不记它属于哪次检查，后来就无法从这次任务找到它。

三台设备只有几条记录，但方案描述的实际场景可能涉及几百个对象和很多检查问题，所以一次提交会包含大量需要保存的数据。

## 原来的慢，出现在两个地方

第一个地方是上传照片。原流程会把照片内容转换成一长串文字，放进业务请求。这种把文件转成文本的编码叫 Base64。它不是压缩图片，不会让原本很大的照片自动变小。请求带着照片内容传输，网络差时容易迟迟传不完。

第二个地方是保存检查数据。照片和数据到了以后，服务端还要逐条写入数据库。如果接口必须等这些操作全部结束才能回复，手机就要一直等待。

你可以用下面的伪代码理解原先的等待方式。这是方案描述的流程示意，不是完整原代码：

```java
上传并保存照片();
for (检查结果 item : 本次提交的所有结果) {
    保存到数据库(item);
}
return 提交成功;
```

手机通常不会无限等待服务器。如果超过它设定的等待时间，就会结束等待，可能提示“提交失败”。这个现象叫“请求超时”。但手机停止等待，不等于服务器立刻停止了保存。因此可能出现：数据库已经保存一部分，手机却不知道保存到了哪里。

## 第一步：照片先上传，检查结果里只带文件引用

方案先调整照片的传法。让手机先把照片上传给专门保存文件的服务，成功后拿到一个文件引用，例如 `photo-demo-001`。

这个引用在方案中叫 `fileToken`。你可以把它理解成找回那份已上传文件所需的标识，不是照片内容本身。名字、实际格式和返回字段以文件服务为准，这里的字符串只是示意。

然后手机再提交检查结果，带上这个引用：

```json
{
  "taskId": 9001,
  "objectId": 1,
  "answer": "发现漏水",
  "fileToken": "photo-demo-001"
}
```

这份 JSON 只用于说明“结果和照片怎样关联”，不是原接口的完整请求。服务器保存业务记录与引用的关系，查看这条记录时再通过文件服务找到照片。

照片仍然需要上传。变化是照片上传和检查结果提交分成了两次处理，业务请求里不再需要重复携带这张照片的完整内容。当前代码存在这样的引用保存路径，也还保留旧的 Base64 处理，不能推定所有手机版本都已切换。

## 第二步：让一部分保存工作在接口返回后继续做

分开照片后，大量检查答案仍然需要写入数据库。方案继续把其中一部分保存工作交给消息队列。

“消息队列”可以先理解为一个专门接收待处理数据的程序。提交接口把要保存的检查数据发给它，另一段后台代码再把数据取出来，执行数据库保存。本项目使用的队列软件叫 RabbitMQ；那段取数据并处理的代码，叫“消费者”。

这样，部分处理变成两段：

```text
提交接口：收到答案 → 把需要后台保存的数据发到队列 → 完成其他必要处理后回复手机
后台代码：从队列取出数据 → 写入数据库
```

“后台”只表示这段处理不要求手机在同一次请求中一直等着，不表示数据已经保存好了。把事情交出去后再继续处理，技术文档常叫“异步处理”；原来等保存完才继续，则叫“同步处理”。

现在你就能理解一个重要区别：手机收到接口的成功回复时，接口这一段可能已经结束，后台保存的明细却还没全部完成。此时立即查询明细，可能暂时看到不完整的结果。

## 当前代码具体做到了哪一步

在 `saveCacheInspectV2` 中，先把收到的提交内容暂存到 Redis。Redis 是另一个能按名称保存和读取数据的程序；这里相当于把“任务编号对应的提交内容”留一份临时副本，代码设置 5 天后过期。

随后，代码检查任务是否已经同步，保存任务等必要数据。任务、随手拍和部分照片关联、缺陷处理仍包含直接写库；检查明细、正常登记、部分附件、扫码和坐标等数据则有发到队列再保存的路径。它不是简单地把整个方法都搬到了后台。

因此，这一轮对原结论的修订是：提交方案已经说明了为什么改——照片让请求大，大量同步写入让等待久；源码也能找到相应处理。但还需要分别确认每类数据怎样保存，不能把“用了队列”写成“所有保存都已经可靠完成”。

## 交给后台以后，还需要解决什么

假设数据库暂时连不上，后台拿到答案却保存失败了，不能因为手机之前收到回复就把数据丢掉。方案提出的几项措施，分别在解决这些具体问题：

| 会发生什么 | 方案想怎样处理 | 术语的意思与当前情况 |
| --- | --- | --- |
| 一条数据处理失败 | 留到专门存放失败消息的地方，再检查原因 | 这个地方叫“死信队列”。当前能看到转入死信和记录日志的代码；放进去不代表已经补存成功 |
| 相同数据被送来两次 | 避免数据库产生两份相同业务结果 | 这种“重复执行也不多产生一份结果”的要求叫“幂等”。现有代码提前分配 ID，并尝试按 ID 保存或更新，但是否覆盖手机重复提交等情况还要验证 |
| 数据库短暂故障 | 等一会儿再尝试保存，并限制尝试次数 | 这叫“延迟重试”。没有找到与本提交流程对应的完整次数控制和重试过程 |
| 某些结果一直没有保存 | 用临时副本核对缺少的数据，再重新发送 | 这叫“补发”。已找到 Redis 暂存，尚未找到完整的定时核对和补发实现 |

这份优化方案写了目标和完成补记，但没有给出“以前等多久、现在等多久”的实际测试数据。我们能讲清楚改造目的及当前能找到的代码，暂时不能填写性能提升百分比，也不能保证各种失败都能恢复。

读到这里，再回头看最开始的提交按钮：它要上传文件、保存任务和大量答案，还要面对网络和数据库失败。理解这些工作之后，附件引用、消息队列、重试等技术才有了具体用途。

## 证据的时点和强度

文档“存储逻辑优化”标题仍写“进行中”，紧接着出现“2025-05-28 15：00已完成此优化项”。本轮将前者保留为原标题，将后者作为较晚状态补记；它能说明文档报告的进展，不证明所有风险措施同时完成。文件系统修改时间也不能替代实现或上线时间。

文档使用“大幅缩小”“明显提升”“支持海量”等定性表述，没有附请求体大小前后对照、P95 延迟、并发量、失败率或验收样本。因此，本轮提升的是**业务动机与方案演变的证据强度**；性能结论仍标为文档报告，测试和真实效果分别待验证。
