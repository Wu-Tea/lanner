# 项目协作的能力目标

状态：2026-09-22 重塑设计。用户已明确把问题扩大到整个项目协作并授权修改；以下能力组织、POV、交互和验证切片为本轮提案。重塑依据见[方向决定](../../.agent-context/decisions/DEC-2026-09-22-001-project-collaboration-direction.md)。

## 1. 创建这个应用的目的

让人和 Agent 围绕共同项目目标持续完成有价值的工作：共享足够准确的项目认识，理解各自任务与相互依赖，在变化时协调，依据证据判断成果，并让后续参与者接得上。

过去侧重 taskworker：让一个 Agent 做对当前任务。新的产品问题还包含不同参与者、并行或前后任务、决定与实际状态之间是否一致。一次局部成功可能留下整体未解决的依赖；保存全部会议摘要也不一定形成可用的共同认识。

维护者应该更容易回答：我们为什么做这件事、谁负责什么、哪些变化影响当前工作、哪些结果可以相信、现在需要我判断什么。产品最终要减少重复说明、追问、冲突返工和记录维护负担。

## 2. 六条能力路线

| 编号 | 能力 | 输入与可见结果 | 完成边界 |
| --- | --- | --- | --- |
| C1 | 调查项目并建立模型 | 项目源码/目标资料 → 用途、功能、模块、流程、规范、来源与未知 | 无旧记忆也能开始，整体覆盖可核对，关键关系有依据 |
| C2 | 结合模型整合资料 | 需求、设计、反馈、历史记录 → 对应主题、新认识、差异及影响 | 区分意图/实现/证据，冲突和材料覆盖可见 |
| C3 | 为新任务或接续任务建立共同理解 | 请求、模型、当前工作与决定 → 目标、相关知识、owner、依赖和完成条件 | 符合用户原意，掌握与本任务有关的新变化 |
| C4 | 在工作中复用知识并协调变化 | 实际动作、问题、纠正和其他工作变化 → 适用知识、影响判断、阶段记录和协调动作 | 关键选择前复核前提；重要偏差、阻塞和并发冲突不被遗漏 |
| C5 | 核验并记录任务与 session 结果 | 可见活动和实际产物 → 分段记录、条件判定、决定、未完成项、知识候选 | task/session 状态分别正确，结论不强于证据 |
| C6 | 综合工作线并更新共享认知 | 多任务记录、当前模型、决定、证据 → 演变、当前状态、依赖、待决定与下一动作 | 综合可追溯且不过期，更新对应 owner，后续工作能实际使用 |

人的理解和使用贯穿六条路线：首次模型、任务交付和工作线报告都应帮助读者做出下一判断。资料生成与理解收益单独验证。

## 3. 首次接入的两种起点

已有项目从可访问源码、配置、构建、测试、现有文档和决定开始；从零项目从目标、约束和设计开始。前者解释已实现结构，后者保持拟议结构与事实的区别。

全项目范围包含所有第一方模块及影响行为的配置、构建/部署和测试；第三方、生成物和外部系统记录调查方式或排除理由。说明已发现、已理解、待补查及受限区域。分批调查可以接续，局部结果不冒充全项目完成。

模型至少连接用途、输入输出、模块职责、关键行为、数据/状态所有权、外部依赖、相关规则、可复用能力和重要未知。源码支持当前行为，设计原因需要相应来源。目录树、标签列表和一份摘要不能单独满足建模要求。

## 4. 人怎样使用

首个验证范围建议为单项目的一人多会话及小团队，每个人可以使用自己的 Agent；多用户共享、身份映射与事件覆盖尚未实现。

用户可以说“接入这个项目”“这份说明影响哪里”“继续提交优化”“目前这条线还卡在哪里”。Agent 组织所需信息，用户不必管理 POV、知识 ID 或会议标签。

普通任务只展示目标、相关前提和结果。涉及多人或跨任务时，再展开 owner、依赖、变更及需要人决定的事项。无实际变化时不产生反复状态打扰。已有明确授权持续有效。

## 5. 协作中的五个 POV

项目认知者维护整体模型；任务执行者完成当前工作；会话记录者保存可见活动及变化；工作线管理者综合并协调；结果核验者检查目标、证据和状态。它们是可切换责任，不是已确定的五个服务或五个并行 Agent。

人类掌握目标、优先级、跨人承诺、重要取舍和风险接受。执行者可以计划自己的工作；manager 的调度能力来自具体授权。对象和权限以[协作契约](../contracts/project-collaboration-contract.md)为准。

## 6. 会议、标签与知识的关系

对齐、讨论、决策、执行、核验和复盘是活动目的，决定本段工作应产出什么。session 可以包含多种活动；task 可跨 session；工作线跨 task/module 组织同一持续目标。

模块和功能的稳定身份由项目模型提供。session 提出 tag 和关联，manager 结合任务引用、依赖、scope 和决定判断相关性。不能只按同标签合并，也不能漏掉跨标签的真实影响。

迭代中的直接获取保留当时需求、条件和观察；事后复盘连接跨阶段结果。二者通过相同的知识准入更新 Base，保留当时认识与后来解释的区别。

## 7. 怎样才算更完善、更好用

保留用户原有要求：比实际使用的 agent-context-sync 更完善、更好用，并方便传播。能力数量和会议数量不证明收益。

| 比较维度 | 需要观察的结果 |
| --- | --- |
| 单任务基线 | 不丢接续、规范、来源、用户纠正、核验与隐私边界；普通工作仍轻量 |
| 跨任务协作 | 降低过期决定、依赖遗漏、重复实现、错误完成声明和冲突覆盖 |
| 人的判断 | 能定位当前状态、受影响工作、证据和需要自己决定的事项 |
| 持续使用 | 新会话和来源变化后仍能正确使用知识，记录与阅读成本可接受 |
| 接入与传播 | 安装、配置、更新、停用与资料保留方便，真实成本有记录 |

对照应给基线相同项目来源、规范、权限和任务输入；使用现有团队工具时保留其功能，不能人为弱化基线。观察人工纠偏、找资料、等待/返工、运行消耗与使用意愿。没有数据时不承诺节省比例。

## 8. 旧能力怎样保留

| 历史编号 | 旧能力 | 新路线中的位置 |
| --- | --- | --- |
| PC-G0 | 首次建模 | C1，资料补充由 C2 持续修正 |
| PC-G1 | 保持任务方向 | C3/C4，并连接项目目标与变更 |
| PC-G2 | 使用相关知识 | C3/C4，包含其他任务产生的新决定 |
| PC-G3 | 核验交付 | C5/C6，局部和整体完成分别核验 |
| PC-G4 | 知识捕获与准入 | C2/C4/C5/C6 |
| PC-G5 | 帮助人理解项目 | 全路线的人类输出与真实使用验收 |

历史案例与编号继续用于回归，不表示新能力已通过验证。旧四项治理责任成为整个协作设计的底层约束。
