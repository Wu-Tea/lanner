# 一条工作线怎样跨会话推进

状态：2026-09-22 合成设计例子。借用“巡检提交”说明协作语义，所有参与者、任务、决定和事件均为虚构输入，不描述原巡检项目的真实实施进展，也不授权修改该项目。

## 1. 从用户能看到的行为开始

检查员在手机上填写一次设备检查结果并上传照片。手机显示提交状态，服务器保存结果，后台人员稍后查看。现在要解决的问题是：手机显示成功时，后台应能找到完整结果；尚未完成时，检查员应知道真实状态。

这就是工作线 W1“提交可靠性改进”的目标 G1。它涉及手机端、提交接口和后台查看，横跨多个模块。业务负责人甲决定成功含义并验收；开发者乙负责手机端任务，甲的 Agent 负责服务端调查和修改。两人的 Agent 均只能使用获授权项目来源。

系统先调查项目，建立“手机提交 → 接口接收 → 保存记录 → 后台查询”的模型。每条关系带来源，尚未运行的行为保持未验证。一份补充设计说明提出采用异步处理；它进入模型时保留“提案”状态，不能覆盖源码仍然同步处理的事实。

## 2. 先把工作分成可判断的任务

| 对象 | 目标与完成条件 | 责任和依赖 |
| --- | --- | --- |
| G1 / W1 | 检查员得到真实提交状态，后台能查询完整结果；需真实联调与业务接受 | 甲拥有业务决定与最终验收责任 |
| T1 服务端状态 | 定义并实现受理/完成/失败状态和查询入口，相关测试通过 | 甲的 Agent 在授权内执行；接口含义由甲确认 |
| T2 手机显示 | 根据接口状态显示准确提示，并在真实链路验证 | 乙及其 Agent 执行；依赖 T1 接口决定和可用实现 |

任务与依赖由实际工作需要产生。无需把“上传照片”“打开页面”等每个动作都变成管理对象。工作线的完成条件独立于两项任务的局部测试。

## 3. 四段 session 中发生什么

### S1：先讨论，再作出决定

甲与 Agent 讨论两种提示方式。甲明确决定 D1：接口接收请求时显示“已受理”，只有确认保存后才显示“已完成”。Agent 形成 T1 的执行计划，并记录 T2 所需的接口约定。

会话记录保存讨论候选、D1 的确认来源、相关任务、当前未知和下一动作。给本段打上“提交/状态”标签，但同时引用 W1、T1、T2 和 D1。S1 结束，两个任务都还未完成。

### S2：乙开始实现，中途发现依赖缺口

乙的 Agent 从 T2 进入，读取与手机显示有关的模型、D1 和 T1 状态。它完成页面结构，但查询入口尚未可用。它报告“页面已实现，联调受阻”，留下依赖解除条件，不把任务标为完成。

同一 session 还讨论了 T1 接口错误码，所以 S2 同时关联 T1 和 T2。一个 session 不能只有一个 task 的假设在此失效。

### S3：甲修改决定并交付局部结果

测试发现需要在多次查询之间识别同一请求。甲确认 D2：查询必须使用提交标识；D2 修订 D1 的接口前提，但保留“受理不等于完成”的业务含义。

T1 的局部测试通过，交付含提交标识的查询接口。记录必须说明 D2 影响哪些约定、T1 的证据范围，以及 T2 仍基于旧接口的事实。D1 的历史保留，被替代的部分明确标出。

### S4：乙恢复任务并核验整体链路

乙说“继续手机提交页面”。Agent 根据 T2 的旧 read basis 和当前 D2 找到变化，先调整调用前提，再进行联调。新的任务上下文应解释为什么需要这项调整，而不让乙重述 S3 的内容。

若联调环境不可用，则 T2 保持缺少联调证据，G1 也尚未完成。若联调通过，还要根据既定完成条件取得甲的业务接受。会话结束与这些状态分别记录。

## 4. manager 在 S3 后应该说什么

> 工作线目标仍是让检查员看到真实提交状态。服务端局部实现和测试已完成，证据限于 T1。接口新增提交标识，甲确认的 D2 修订了原约定，手机任务 T2 需要据此调整。当前没有端到端联调证据，整体目标尚未完成。下一步是乙恢复 T2 并核对新接口；如果已有授权不包含这项范围变化，则先给甲提供具体影响和选择。

这份报告引用 T1/T2、D1/D2 和测试来源，并说明它只覆盖 S1–S3。它不能说“项目优化完成”，也不能未经授权替乙承诺交付日期。

## 5. 如何判断相关会话

另一个 session 讨论“导出任务状态”，即使也有“状态”标签，只要没有相同目标、接口或依赖，就不应并入 W1。另一个标记“网络层”的改动若改变提交标识传递，则可能直接影响 T2，即使标签不同也应纳入影响调查。

标签帮助找候选，稳定主题、任务/决定引用、依赖、scope 和来源帮助判断关系。manager 负责综合解释，确定性记录机制负责避免同一来源重复入库或旧版本覆盖新决定。

## 6. 留给后续工作的东西

工作记录保留会话活动、任务状态、依赖和验收。长期 Base 可以接纳“受理与完成的业务区别”“接口需要提交标识”“相关验证入口”等可复用知识，并保持决定与证据来源。

下一次修改后台提示时，Agent 可按该行为取回这些知识并复核；新人可以阅读一张提交流程与一段状态说明，判断改动会影响哪里。完整会话和每一步尝试无需全部复制进 Base。
