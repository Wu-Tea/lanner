# 面向人的项目与协作资料

状态：2026-09-22 设计；真实读者效果未验证。

## 1. 资料服务什么判断

让维护者或新成员理解项目行为、当前工作、变化影响和待决定事项。先回答当前问题，再展开证据。技术项目资料使用 Base；进展与协作资料引用工作状态和决定来源，信息归属见[所有权契约](projection-ownership-contract.md)。

## 2. 按问题选择表达

| 人的问题 | 适合的内容 |
| --- | --- |
| 这个项目实际做什么？ | 用途、输入输出、完整行为、主要结构与未知 |
| 我这次要做什么？ | 当前目标、相关前提、范围和完成条件 |
| 这条工作线现在怎样？ | 目标、最近变化、已完成/未完成、依赖和下一动作 |
| 为什么改变了方案？ | 当时依据、决定、实际结果、后来认识及来源 |
| 改这里影响谁？ | 相关模块、任务和参与者，明确关系与条件 |
| 现在需要我判断什么？ | 具体命题、选择、证据、影响与建议 |

连续解释用文章，行为顺序用流程，演变用时间线，依赖用局部关系，选择用比较表。默认不铺满全仓库关系或全部管理指标；不要求每次任务生成多份资料。

## 3. 阅读顺序与完整例子

先说明可观察用途、输入和结果，再讲一次从开始到结束的行为，随后解释其中模块、规则和失败方式。新术语先用具体角色解释；不按类名或调查顺序倾倒材料。

任务与工作线资料先说明当前焦点、相较上次变化和主要下一动作，再展开历史与证据。进入细节后保留父问题和返回入口。采用明确的读者前提；巡检案例的“零业务、只会 CRUD”范围不自动成为所有产品用户的前提。

## 4. 状态与依据

观察、推断、提案、确认、未验证、过期和未知可区分。正文保持流畅，关键结论按需打开来源、scope、revision 和限制。工作线总结显示覆盖时点；未读到的会话和受限来源说明缺口，不补写内容。

标签仅作定位线索；关系要有有意义的动词、方向、scope 和依据。间接依赖保留必要路径，不能把共同标签画成已证实因果。

## 5. 验证人的使用

让真实读者完成一个与其职责相符的问题：复述用途、定位一条行为、判断一个影响、识别一个未知或指出下一决定。记录资料版本、读者前提、回答、额外解释和可获得用时。

模型模拟标为合成评估。资料生成、语义核验、真实理解和长期收益分别验收；读者能复述文章不必然说明能作出维护判断。若资料引出新语义，回到对应 owner 修正。

## 6. 历史材料

`docs/examples/` 的文章、多视图 fixture 和旧 UI 作为研究材料保留，不冻结本轮对象、布局或技术。案例资料与独立 Demo 保留自身验收范围。
