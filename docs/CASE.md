# 开发案例：报表导出改为异步后，怎样让相关任务跟上变化

一位开发者通过多个 Agent 会话完成报表导出功能。开发过程中，后端从同步返回文件改成后台生成，前端与测试也需要相应调整。本文沿着这次变更，说明分散工作的管理成本从哪里产生，以及 Project Cognition 准备怎样提供支持。

这是用于解释设计的假设案例。下文的项目目录、接口、会话记录和检查结果均为示意，不是本仓库已有实现或实际运行记录。产品能力与范围见 [MVP](MVP.md)。

## 一、开发任务与最初方案

假设项目是一个已有报表页面的 Web 应用，现在需要增加 CSV 导出：用户按日期筛选数据，点击导出，下载与筛选条件一致的文件。项目也已有供其他功能使用的后台任务模块和文件存储模块。

相关代码位置假设如下：

```text
web/src/pages/Reports.tsx          报表页面
web/src/api/reportExports.ts      前端导出请求
server/routes/report_exports.py   导出接口
server/jobs/                      后台任务
server/storage/files.py           文件存储
tests/report_export/             导出相关测试
```

开发者将“完成报表导出”作为一个任务，由三个会话分别承担后端、前端和测试工作。三个会话共享目标和完成条件，各自接收与分工相关的材料。本文所说的导出接口创建的后台任务，是应用内部的作业，不是这里的开发任务。

最初设计约定：前端提交筛选条件，后端在当前请求中生成 CSV 并返回。前端将响应作为文件下载，测试检查响应类型和 CSV 内容。

```http
POST /api/report-exports
Content-Type: application/json

{"startDate":"2026-09-01","endDate":"2026-09-22"}
```

预期响应为 `200 OK`，内容类型为 `text/csv`。到这里，前端、后端与测试使用的是同一份约定。

## 二、一次局部决定怎样造成整体返工

在后端会话中，Agent 调查后提出：大范围导出可能超出当前请求的等待时间，应改为后台生成。开发者确认采用异步方式，后端工作据此继续推进。

新的接口约定变为：

| 步骤 | 接口与返回内容 |
| --- | --- |
| 创建导出任务 | `POST /api/report-exports` 返回 `202 Accepted` 和任务编号，不再返回 CSV |
| 查询生成状态 | `GET /api/report-exports/{id}` 返回排队中、处理中、成功或失败；成功时附下载地址 |
| 下载文件 | 前端在成功后使用下载地址获取 CSV |

创建任务的响应示意为：

```json
{"id":"export-123","status":"queued"}
```

这项决定发生在后端会话，却改变了三项工作的共同前提。如果决定只保留在那里，前端和测试仍可能沿用原方案。

前端将所有成功响应直接作为文件下载，就可能把这段 JSON 保存成 CSV。前端本地使用的模拟接口仍返回 CSV，因此页面检查可能通过。测试会话也可能继续维护“创建请求应返回 200 和 CSV”的旧断言。联调时，才暴露出前端行为、后端实现和测试预期不一致。

| 工作 | 各自认为完成了什么 | 尚未对齐的部分 |
| --- | --- | --- |
| 后端 | 能创建后台任务并生成文件 | 前端和测试是否已经接收新约定 |
| 前端 | 点击按钮后可以下载模拟文件 | 真实响应已变为任务编号，还需要查询状态 |
| 测试 | 已按原方案编写断言 | 测试依据已经被新的决定替代 |

开发者随后需要查找变更发生在哪个会话，解释调整原因，分别修改任务背景，再核对哪些实现和检查仍然有效。几天后如果换一个会话继续开发，还需要确保旧设计不会重新成为当前依据。

另一项可能的重复成本来自项目理解：如果后端 Agent 没有发现已有后台任务模块，就可能新建一套调度逻辑。即使后来同步好了接口，也仍需判断两套实现是否应合并。

这类返工的根源是：任务依赖的共同认识已经变化，相关任务却继续使用各自保存的旧前提。执行速度越快，基于旧前提完成的工作也可能越多。

## 三、Project Cognition 怎样介入这次开发

### 先让任务获得已有项目背景

首次调查项目时，整理报表页面、导出接口、后台任务和文件存储的职责及关系，并保留代码位置与未知。后端工作开始时，可以据此找到已有后台任务能力，进一步检查它是否适合报表导出。

找到模块不等于确认能够直接复用。任务仍需核对处理方式、运行条件和已有约束；尚未检查的部分明确保留。项目模型提供可继续调查的依据，避免每个会话都从目录重新猜测。

最初的同步导出设计也关联到报表功能和三项工作，标明它是当前约定。这使后续变更有明确的比较对象。

### 将确认的决定与实施进度分别记录

开发者确认异步方案后，后端会话提取并保存影响后续工作的信息，而不是只留下一句“已改成异步”。记录内容可如下所示：

| 内容 | 本案例中的记录 |
| --- | --- |
| 决定 | 导出改为后台生成，创建请求返回任务编号 |
| 确认来源 | 后端会话中开发者确认采用异步方式的原始消息 |
| 变更理由 | 大范围导出存在超出请求等待时间的风险；具体容量仍需验证 |
| 被替代的约定 | 创建请求直接返回 CSV |
| 影响 | 前端请求处理、状态展示、下载流程和接口测试需要调整 |
| 当前实施情况 | 根据实际改动和检查记录另行更新，不能由决定本身推定完成 |

会话标注“报表”“导出”“后台任务”等标签，并关联具体任务和接口。长期资料保留已确认的设计变化及来源，工作记录继续维护各项工作的实施状态。

### 找出受影响的工作，并在接续时使用新要求

项目协调者读取变更记录，结合项目模型确认：前端导出请求调用了这个接口，相关测试检查了它的返回内容，因此两者都受影响。

标签帮助查找，但不能单独作出结论。另一个同样标注“后台任务”的邮件发送任务，如果没有依赖这次修改，就不应被要求调整；前端工作即使只标注了“报表页面”，也能通过接口调用关系被找到。

第一版允许开发者手动发起整理，并在继续前端工作时明确读取更新后的背景。它不承诺能够主动打断另一个正在运行、尚未接入的会话。

前端工作接续时，应获得具体变化及待办：创建请求不再返回文件，需要保存任务编号、查询状态、处理失败，并在成功后下载。测试工作则更新相应的接口预期。Agent 根据现有代码自主决定实现方式，无需开发者重新转述完整讨论。

### 在同一任务内看清谁在做什么

接口变化之外，还要维护三个会话的当前分工。假设后端检查已完成，前端正在调整，测试会话已经准备好新的检查项，等待前端接入：

| 任务内的工作 | 当前承担会话 | 工作状态 | 依据或下一条件 |
| --- | --- | --- | --- |
| 后台生成与状态接口 | 后端会话 | 本项已完成 | 对应版本的后端改动和检查记录 |
| 状态展示与下载衔接 | 前端会话 | 实施中 | 最新进展已记录；是否仍在运行取决于可用的活动信息 |
| 完整导出流程验证 | 测试会话 | 等待依赖 | 等待前端接入和可运行的集成版本 |

表格表达的是假设状态，实际使用时每项依据都要能找到来源。后端会话结束不会将整个任务关闭；测试等待集成版本，也不会阻止前端继续实现。开发者可指定测试会话承担最终结果核验，由它检查共同完成条件并提交结果。

如果前端会话中断，接手会话先读取现有改动、当前接口约定和未完成部分，再按确认的分工继续。原前端会话后来恢复，应先发现承担者和版本已经变化，不能把旧状态直接写回，也不能无意中与接手者同时修改同一份代码。

如果后端再次修改查询结果中的状态字段，manager 应指出前端处理逻辑和测试断言受到影响，并跟踪相关会话是否已经读取和调整。即使某项工作此前完成，受到这次变更影响的检查也需要重新核对。

第一版可用顺序调用演练这些情况。只有在共享工具实际支持认领确认和版本检查后，才能进一步验证两个会话同时操作时是否可靠。

### 用实际依据判断整体完成程度

假设某一时点，后端已完成任务创建、状态查询和文件生成检查，前端尚未完成状态展示，完整流程也还没有运行。协调报告应表达这个具体状态：

> 异步导出方案已确认。后端实现与后端检查已完成；前端仍需完成状态展示和下载衔接。完整导出流程尚未验证，因此当前不能将报表导出功能标为完成。下一步是完成前端接入，再检查创建任务、后台生成、状态查询和文件下载能否连通。

这段话是假设状态下的报告示意。实际使用时，“已完成”和“检查通过”必须引用对应改动、项目版本与检查记录；没有这些依据，就应标为待核对。

最终验收还要回到用户最初的要求：下载的文件是否包含筛选后的正确数据。接口能够返回任务编号、后台能够生成文件，分别只证明了部分条件。

### 把经过核对的认识用于下一次工作

本次任务完成后，长期保留导出流程、相关接口、后台任务与文件存储的关系，以及验证过的适用条件。旧同步方案保留被替代的记录，避免它在检索时再次被当作现行要求。

以后新增其他导出需求时，Agent 可以找到这些能力，再判断能否复用。临时调试的全部过程继续留在原任务中，不必复制进每个新任务的背景。

## 四、要减少哪些管理工作

| 原来需要开发者亲自承担的工作 | 希望由项目能力提供的支持 | 开发者仍需判断的事情 |
| --- | --- | --- |
| 反复查找现有模块并补充背景 | 项目调查结果为任务提供相关代码、资料和能力线索 | 调查缺口及方案是否适合当前需求 |
| 到多个会话中转述接口变化 | 提取决定、识别影响，并在相关任务接续时提供更新 | 是否确认方案变化及其业务取舍 |
| 逐个比对 Agent 的完成汇报 | 将任务状态与实际产物、检查记录放在一起核对 | 未满足条件是否需要继续处理，结果是否可以接受 |
| 重新整理最终方案供以后使用 | 将具有后续价值的认识更新到长期项目资料 | 重要结论是否准确、是否需要修正 |

这里的价值取决于管理总负担是否下降。整理、读取和修正记录也有成本；如果维护这些材料比开发者直接沟通更费力，就不能仅凭记录更完整声称方案有效。

## 五、怎样用这个案例做后续验证

可以在具有导出需求的真实项目中，按同样的工作顺序记录一次开发过程：先提供原接口约定，再在后端工作中形成变更，随后恢复前端和测试工作。恢复时不直接告诉它们期望修改的答案，检查它们能否从项目资料与工作记录中找到变化。

重点观察：

- 是否找到了已有后台任务能力，并核实了复用条件。
- 前端与测试是否在继续工作前读取新决定，而非联调失败后才获知。
- 是否正确区分了会话活动、各项工作进展和整体完成，并保留最终整合与核验依据。
- 分工重叠、依赖等待、中断接手和旧会话恢复时，是否能够保持现行安排，避免重复工作或覆盖新结果。
- 新任务能否继续使用最终方案，并识别旧方案已被替代。
- 开发者补背景、转述、纠偏和核对所花的精力，是否足以抵消新增的记录维护与模型成本。

实际运行时记录失败与未覆盖部分，不以案例中的预期结果代替观察。如果只有合成材料，只能说明该判断过程在演练中的表现。完整验证要求见[验证说明](VALIDATION.md)，信息与职责的设计见[设计说明](DESIGN.md)。
