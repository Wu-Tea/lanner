# 变更协作范式：共享能力变化后，怎样让相关工作跟上

一项共享能力发生变化，可能同时改变实现方、使用方和核验工作的共同前提。本文说明如何发现影响、接续工作并核对整体结果。它是通用解决方案，不包含具体项目实例，也不代表已有运行结果。产品目标见 [MVP](MVP.md)。

## 一、明确共同目标与已有关系

项目模型说明能力的用途、适用条件、实现依据及使用关系。任务保留原始请求、目标、范围和完成条件，各会话据此确认自己承担的部分、预期产物及依赖。

模型为调查提供入口。发现已有能力后，Agent 仍需核对当前实现与使用条件，才能判断是否适合复用。目录相近或标签相同，不足以证明能够直接复用；不同目录也不意味着没有共同依赖。

## 二、记录变更与被替代的前提

当已确认要求发生变化时，记录变更内容、理由、确认来源、适用范围及被替代的约定。实施进度另行记录，决定已经保存不代表改动已经完成。

| 信息 | 作用 |
| --- | --- |
| 旧前提与新要求 | 让接续者知道哪里发生了变化 |
| 确认来源与授权范围 | 判断该变化对当前工作是否有效 |
| 受影响的能力与关系 | 找到需要重新检查的使用方与工作 |
| 对应产物与验证依据 | 判断实现和结果是否已经符合新要求 |
| 未知与待处理事项 | 防止缺失信息被误当作已经解决 |

## 三、定位影响并接续相关工作

manager 从变更涉及的能力出发，结合实际依赖、引用和工作目标识别影响。共同标签仅用于查找；没有依赖的工作不因标签相同而被要求调整，没有共同标签的真实使用方也不能遗漏。

相关会话继续工作前，读取当前要求与分工，核对自己的前提是否变化，再自主决定实现和检查方法。变更已保存、会话已读取、工作已调整分别需要依据。尚未接入的会话不能被假定已经收到更新，文档保存也不提供实时通知。

共同要求变化后，原来已完成的工作可能需要复核。保留原完成记录及当时条件，标明受影响部分，不直接把旧结论沿用到新版本。

## 四、协调分工、等待与中断

同一任务内分别维护各项工作的承担者、范围、依赖、产物和状态。已知的活动记录注明时间与来源，缺少当前活动信息时保留未知。

| 协作情况 | 处理方式 |
| --- | --- |
| 实现方已完成局部修改 | 关联产物与检查，不据此关闭整个任务 |
| 使用方正在适配 | 保留最新进展；是否仍在运行由活动依据确认 |
| 核验工作等待集成 | 说明所需产物和解除条件，其他独立工作可以继续 |
| 多会话修改重叠内容 | 明确协作边界、修改顺序或整合方式 |
| 中断后由其他会话接手 | 按授权更新承担者，保留当前结果与未完成部分 |
| 旧会话恢复 | 先核对现行分工与版本，不能用旧状态覆盖接手后的安排 |

顺序交接可以先验证这些信息是否足够。真正并行时还需对应工具提供认领确认和版本检查，不能用文字约定代替并发保障。

## 五、判断整体结果并保留可复用认识

任务完成需要相关产物已经整合，整体条件在当前版本得到核验，并取得任务约定要求的接受。实现存在、局部检查通过、执行者声明完成和实际效果成立分别表达。

manager 汇总哪些条件满足、哪些不满足、哪些尚未验证，说明依据与下一步。多个局部完成声明不能相加成整体完成，也不在缺少可解释基础时生成完成百分比。

有跨任务价值的能力认识、有效约定、依赖和经验，经核对后进入 Base；临时进展继续由工作记录维护。保留被替代关系与适用条件，让后续任务能够识别旧前提，并判断经验是否适用。

## 六、如何检验这一范式

在授权范围内安排共享要求变更、使用方接续、依赖等待、中断交接和最终核验。恢复任务时不直接提供期望答案，观察会话能否从项目模型与工作记录找到变化及影响。

同时统计遗漏、重复工作、错误完成判断，以及开发者补充背景、协调和纠偏的投入。将模型整理、记录维护和额外调用计入总成本。合成演练与真实使用分开报告，完整比较方法见[验证说明](VALIDATION.md)，信息归属与职责见[设计说明](DESIGN.md)。
