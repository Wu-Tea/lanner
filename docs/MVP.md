# MVP：让一条工作线跨会话可靠推进

状态：2026-09-22 设计提案，尚无产品运行。用户确认的是项目协作方向及精简要求，以下能力组织和首轮切片仍需通过真实工作验证。

## 目标

让参与者知道项目怎样工作、当前任务为什么做、依赖什么、新变化影响哪里、成果有哪些证据，以及下一步需要谁判断。单人跨会话也适用；整个产品应比实际使用的 agent-context-sync 更完善、更好用，并方便接入和传播。

## 能力范围

| 能力 | MVP 要提供的结果 |
| --- | --- |
| 1. 项目建模 | 从源码或目标资料建立用途、模块、关键流程、规则、来源与未知；不依赖旧会话 |
| 2. 整合附加资料 | 把需求、设计、反馈连接到项目模型，识别新增认识、冲突和影响 |
| 3. 理解新任务或接续任务 | 保留原意，确定相关知识、责任、依赖、范围和完成条件 |
| 4. 工作中使用与更新认知 | 关键选择前复核旧经验及新决定，及时记录偏差、纠正和阶段证据 |
| 5. 记录并核验结果 | 分清交流、决定、实施与验证，保留任务/session 各自状态和未完成项 |
| 6. 综合工作线 | 串联多个任务与会话，说明变化、进展、依赖、冲突和下一动作，形成知识候选 |

资料应帮助人判断项目行为、工作进展和改动影响；生成成功不代表读者已经理解。

## 首个切片

先选择一个获授权的真实项目、一条工作线、两项有依赖的任务、至少三段 session、一份附加资料和一次明确决定变化。先验证一人跨会话，实际多人、权限与并发另行验证。

1. 调查项目，形成有来源的模型和覆盖说明。
2. 整合附加资料，区分设计意图与当前实现。
3. 明确工作线目标、两项任务、责任、依赖和完成条件。
4. 任务推进中出现新决定，恢复旧任务时能发现其影响。
5. 分别核验局部与整体结果，生成可追溯的工作线综合。
6. 在后续任务与一个真实维护者问题中观察知识是否有用。

首次建模覆盖整个指定项目，列明已理解、待补查、排除原因与外部盲区；分批结果不能冒充全项目完成。从零项目先建立意图/设计模型，再随实现增加事实。普通局部任务不强制全项目重扫。

## 一个完整例子

以下为合成说明，不表示原巡检项目实际发生过这些工作。

检查员提交检查结果，手机需要区分“已受理”和“已完成”。负责人甲决定业务含义；甲的 Agent 做服务端任务 T1，乙及其 Agent 做手机任务 T2，T2 依赖 T1 的接口。

- S1：讨论后甲确认 D1，明确两种状态。会话结束，两项任务均未完成。
- S2：乙完成页面结构，查询接口尚不可用，T2 保留联调阻塞；同一会话也讨论 T1 错误码。
- S3：甲确认 D2，新增提交标识要求；T1 局部测试通过，但 T2 仍基于旧接口。
- S4：乙恢复 T2，读取 D2 并调整调用，再核验端到端行为。环境不可用就保留未验证，不能宣布整体完成。

S3 后 manager 应说明：“服务端局部完成；D2 影响手机任务；整体缺联调证据；下一步是恢复 T2 并核对新接口。”它引用任务、决定和测试，不能替乙承诺交付日期。同标签的其他工作不自动并入；无共同标签但改变该接口的工作需要检查影响。

## 首轮边界与推进

先使用显式导入和调用，允许人工连接来源，诚实记录手工成本。对象、权限和准入见[设计](DESIGN.md)，验收见[验证](VALIDATION.md)。

暂不实现企业组织树、跨项目资源组合、日历、复杂排期、人事绩效或自动外部通知。无需预先部署五个 Agent、向量/图数据库或通用源码解析器。宿主、持久化、界面和分发方式按验证缺口选择。

下一步先固定真实项目/revision、材料权限、参与者、任务条件、核验方式与预算，再用最小记录路径开展一次运行。根据真实失败补工具，随后验证复用、多人和成本收益。当前没有启动运行或选定技术栈。
