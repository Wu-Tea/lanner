# 验证说明：是否减少了项目管理负担

第一轮要回答的问题是：一个开发者使用 Agent 推进相关工作时，Project Cognition 能否帮助他正确接续任务、掌握变化和判断结果，同时减少管理这些工作的总负担。

验证从单人跨会话使用开始，再检查后续复用，最后扩展到多人协作与工具接入。本文规定各阶段需要收集什么依据；目前尚未选定试用项目，也未执行产品验证。

## 一、第一轮验证什么

选择一个真实项目，由一位开发者通过多次会话推进两项相关任务，其中至少一项由不同会话分工或交接完成。过程中接入补充资料、修改一项已确认要求，并在恢复任务和汇总进展时检查这些信息是否被正确使用。允许手动提供记录和发起整理。

这一轮覆盖项目调查、资料整合、任务接续、变化记录、协调和结果核验。观察重点包括：

| 检查内容 | 需要观察到的结果 |
| --- | --- |
| 首次理解项目 | 不依赖旧会话，调查指定的整个项目，说明主要功能、结构和关键流程，找到来源并标出未理解部分；只有目录摘要不足以证明理解 |
| 整合补充资料 | 区分需求、拟议方案与已有实现，指出差异及受影响的工作 |
| 跨会话接续 | 一个任务分多次会话、一次会话涉及多个任务时，目标、状态和待办仍然对应正确 |
| 同一任务的分工 | 能找到各项工作的承担者、范围与产物；遇到重叠时明确协作或接手关系，局部完成不覆盖整个任务 |
| 活动与完成程度 | 旧活动记录不冒充实时执行状态；缺少当前信息时标为未确认，不据此自动释放分工或接管 |
| 依赖与交接 | 等待有具体解除条件，其他可独立工作继续推进；中断后接手者能继续，旧会话恢复时先核对分工与版本 |
| 变更同步与重新核验 | 分清变更已保存、有关会话已读取和工作已调整；完成后受新变化影响的部分需要重新核验 |
| 记录讨论与决定 | 能分清讨论过、已经决定、完成实施和已经接受，保留各自来源 |
| 识别关联工作 | 标签相同但内容无关时不误联，没有共同标签但确有依赖时不漏联，改名后仍能找到原记录 |
| 处理要求变化 | 恢复任务或采取关键行动前发现有关变化，重新检查前提并按授权调整 |
| 判断完成程度 | 各部分均报完成后仍核对整合结果与整体条件，缺少依据时保持未完成或尚未验证 |
| 处理中断与缺失 | 保留已知阶段结果和恢复动作，不补造缺失记录或结论 |
| 协调相关任务 | 指出等待、冲突、共同资源限制及需要人决定的事项，不虚构排期、责任或承诺 |
| 支持人的判断 | 开发者能根据记录判断当前状态、影响和下一步，普通小任务的记录负担可接受 |

真实任务不一定自然出现所有情况。缺失的情况可以用合成材料单独检查，但必须区分合成检查与真实运行，未覆盖部分继续保留为待验证。

同一任务的协作先用明确调用、顺序更新和中断交接验证。模拟两份旧记录可以检查是否正确识别冲突，但不能证明真实并发安全；同时认领和同时写入需要后续工具测试。

## 二、怎样执行和核对

### 开始前确定条件

记录项目版本、原始请求、两项任务的目标与依赖、任务内分工及结果整合与核验责任、初始资料和决定，以及参与者能够访问的内容和已有授权。同时确定模型、运行工具、会话输入顺序、预算和核验方式，使结果能够对应到当时的条件。

任务的完成条件与成本可接受标准在运行前确定。具体标准随项目和任务设定，不预设通用节省比例；看到结果后如需调整，说明理由并保留原标准，不能用新标准替代旧结果。

### 按真实工作推进

先调查项目、建立初始认识，再将补充资料用于任务理解。执行中记录变化，恢复任务时核对新要求，结束时检查实际产物和未完成项，最后汇总两项任务的整体情况。

后续会话应通过项目资料和工作记录取得背景，不预先把期望答案写进任务请求。若需要开发者补充信息或纠偏，如实记录内容和花费。

### 对照原始依据判断

检查者对照代码、决定、实际产物和测试记录判断结果，不能只用另一份生成摘要验证当前摘要。语义是否正确需要结合材料和人工判断；实现出现后，引用解析、去重、权限、并发和持久化等确定性行为再用机器测试检查。

每项重要条件分别标记满足、不满足或尚未验证，附上依据、项目版本、环境、检查者及检查方法。Agent 自查、独立核验和使用者接受分别说明，文档检查不作为产品运行成功的证明。

## 三、怎样比较收益与成本

以实际使用的 agent-context-sync、现有项目规则和协作工具作为比较基线。双方采用相同任务、来源、权限与可比资源；记录模型差异、执行顺序和重复做任务可能带来的熟悉程度影响，避免将这些差异误算为产品收益。

同时观察工作质量与管理成本：

| 比较方面 | 记录内容 |
| --- | --- |
| 工作质量 | 目标偏差、遗漏的依赖或决定、错误完成声明，以及冲突造成的返工 |
| 人的投入 | 补充背景、查找信息、纠偏、协调、阅读和核对结果所需的时间与操作 |
| 维护与运行成本 | 整理记录、修正项目知识和额外模型调用的成本 |
| 完成时间 | 按相同的开始与结束条件统计，说明等待和中断 |

使用者还需要独立完成一次实际判断，检查资料是否足以支持下一步，而非仅认为摘要看起来完整。单项成本下降不足以代表总负担降低；收益判断同时考虑质量、维护负担和运行开销，不以 Agent 数量、文件数量或摘要数量代替。

第一轮即开始记录这些成本，并检查普通小任务是否被增加了不必要的步骤。没有可比记录时，只报告观察结果，暂不声称节省了多少。

## 四、后续分两步扩展

### 检查知识能否持续复用

第一轮产生的记录，需要在新的任务中实际使用。检查已有事实、决定和经验是否适用，来源变化后能否识别过期内容，并修正受影响的任务或项目认识。

复盘记录保留当时条件和后来的解释。重复导入同一来源时不应重复产生内容或动作，基于旧资料提出的更新不能直接覆盖新决定。合成演练可以帮助检查这些规则，但后续真实任务中的复用仍需单独验证。

### 检查多人协作与自动接入

具备对应实现与运行条件后，再验证以下能力：

| 能力 | 需要的验证 |
| --- | --- |
| 身份与共享权限 | 使用真实的不同参与者和可见范围，检查检索、记录及输出不会泄露受限内容；Agent 归属不会自动带来项目决定或任务分派权 |
| 并发认领与更新 | 同时认领重叠工作时能确认有效分工；同时写入、旧会话恢复或重复提交不覆盖接手后的有效状态，冲突和处理过程可追溯 |
| 执行状态、自动事件与通知 | 在实际工具中检查运行与停止信息、断连后的未知状态、事件触发与重复处理、缺失记录和按授权通知，并说明覆盖范围 |
| 多人理解与协调 | 不同参与者能根据同一套记录理解状态、责任和依赖，协调建议符合各自权限 |

首轮单人使用仍需遵循已有的隐私与授权要求。将多人验证安排到后续，只表示尚未取得相应运行证据，不表示可以提前开放未验证的共享能力。

## 五、如何记录结论

分别报告合成检查、首轮真实运行、后续复用、多人运行和人的实际收益。每个阶段的通过只支持对应范围的结论，不能替代其他阶段的证据。新增协作能力也不能以牺牲任务原意、规范遵循和可靠接续为代价。

第一轮结束时，应能说明哪些能力得到支持、哪些情况仍然失败、哪些还没测，以及下一步值得验证什么。结果写入已有任务证据和简短项目日志，不为尚未运行的场景新建报告目录。
